Micronaut Runner

Fast-starting single-jar packaging for Micronaut applications (launcher, Gradle and Maven plugins)

Version: 1.0.0-SNAPSHOT

1 Introduction

A Micronaut application is usually shipped as a single executable JAR, and until now that has meant a shaded JAR: Gradle Shadow or Maven Shade copy the contents of every dependency into one archive and flatten them into a single namespace.

Flattening is lossy. Two dependencies that both ship META-INF/services/java.sql.Driver collide, so the build needs a transformer to merge them. Micronaut 4 and later publish their bean metadata as a directory tree under META-INF/micronaut/, which collides the same way. Signature files have to be stripped or the result fails verification. module-info.class files collide. META-INF/versions/ trees from several multi-release JARs are merged into one that belongs to no particular library. Each dependency’s own manifest, and with it Implementation-Version and package sealing, is discarded. Every one of these is a silent failure mode: the build succeeds and the application misbehaves at run time.

Micronaut Runner takes a different approach. The archive it produces is still a single file you run with java -jar, but every dependency inside it remains an intact JAR:

The shape of a runner JAR
app.jar
├── META-INF/MANIFEST.MF          (1)
├── MICRONAUT-INF/index.bin       (2)
├── io/micronaut/runner/*.class   (3)
├── META-INF/micronaut/**         (4)
├── MICRONAUT-INF/classes/**      (5)
└── MICRONAUT-INF/lib/*.jar       (6)
1 Main-Class points at the launcher
2 the index: every entry of every nested JAR, with its byte offset in this file
3 the launcher and its class loader, a handful of classes with no dependencies
4 the merged Micronaut bean metadata, so the framework finds it in one pass
5 the application’s own classes and resources
6 the dependencies, each one a complete, untouched JAR

Because the boundaries survive, so do the semantics. Duplicate resources stay distinct and are returned in classpath order, each JAR keeps its own manifest and package metadata, sealed packages are still enforced, and multi-release JARs still resolve per JAR against the running JDK.

Why it is fast

Reading nested JARs is normally slower than an ordinary classpath, which is why the usual advice for this style of archive is to unpack it before running in production. Micronaut Runner avoids that cost by moving all of the work to build time.

When the archive is packaged, every entry of every nested JAR is recorded in MICRONAUT-INF/index.bin together with its absolute byte offset in the outer file. At startup the launcher memory-maps the archive once and reads that index directly out of the mapping. Looking up a class is a single hash probe followed by a byte comparison; no central directory is parsed, no nested archive is opened, nothing is extracted to disk, and no temporary files are written. Dependencies are stored uncompressed by default, so a class is defined straight from the mapped bytes with no intermediate array and no decompression.

The launcher itself is written to keep off the JVM’s slow paths: no lambdas, no string concatenation through invokedynamic, no reflection on the entry path, and no java.util.logging. It is a handful of classes, and it hands control to your main method through an interface call.

2 Quick Start

Gradle

Apply the plugin alongside the Micronaut application plugin:

plugins {
    id 'io.micronaut.application' version '5.0.2'
    id 'io.micronaut.runner' version '{version}'
}

That is the whole configuration. The plugin adds a micronautRunnerJar task, wires it into assemble, and takes your main class from the application block and your dependencies from the runtime classpath, in resolution order.

./gradlew micronautRunnerJar
java -jar build/libs/my-app-0.1-all.jar

The archive is named with the all classifier, the same name the Shadow plugin uses, so existing Dockerfiles and CI scripts that reference build/libs/*-all.jar keep working.

Do not apply the Shadow plugin and configure it to write the same file. The two produce different archives under one name. The plugin fails the build if it detects that.

Configuration

Every setting is a property of the task:

micronautRunnerJar {
    // Defaults to application.mainClass
    mainClass = 'com.example.Application'

    // STORED re-packs dependencies uncompressed so classes are defined straight from the mapped file.
    // PRESERVE copies each dependency byte for byte, producing a smaller archive that loads more slowly.
    compression = 'STORED'

    // Written into the manifest, so users need not pass the matching command line flags.
    addOpens.add('java.base/java.lang')
    addExports.add('java.base/sun.nio.ch=ALL-UNNAMED')
    enableNativeAccess = true

    manifestAttributes.put('Implementation-Vendor', 'Example Ltd')
}

manifestAttributes may override attributes imported from the application’s manifest. Manifest-Version, Main-Class and every attribute whose name begins with Micronaut-Runner- are reserved for the runner format and are rejected case-insensitively.

Maven

Add the plugin to your build. Bind it to package, so it runs after the JAR is built:

<plugin>
    <groupId>io.micronaut.runner</groupId>
    <artifactId>micronaut-runner-maven-plugin</artifactId>
    <version>{version}</version>
    <executions>
        <execution>
            <goals>
                <goal>package</goal>
            </goals>
        </execution>
    </executions>
</plugin>
mvn package
java -jar target/my-app-0.1.jar

By default the runner JAR replaces the project’s main artifact, exactly as the Shade plugin does, and the JAR produced by maven-jar-plugin is kept alongside it as original-my-app-0.1.jar. Set a classifier to attach it as an additional artifact instead and leave the main one untouched.

The main class is taken from the exec.mainClass property, which the Micronaut parent POM already sets.

What to check first

java -Dmicronaut.runner.mode=inspect -jar my-app-0.1-all.jar

prints the format version, the number of dependencies and entries, and the application main class, which confirms the archive is what you expect before you deploy it.

3 The Runner JAR Format

This chapter documents the archive layout. You do not need any of it to use Micronaut Runner; it is here so the format can be inspected, reimplemented and reasoned about.

Outer archive

Every entry of the outer archive is STORED, that is, uncompressed. That is what allows a nested JAR’s bytes to be read in place at a known offset.

Entry Purpose

META-INF/MANIFEST.MF

Written first. Main-Class is io.micronaut.runner.Launcher. Micronaut-Runner-Format carries the format version, Micronaut-Runner-Start-Class the application main class, for information only.

MICRONAUT-INF/index.bin

Written second, so the launcher finds it after reading only a couple of central directory records.

io/micronaut/runner/**.class

The launcher. Only class files are copied from the launcher library; its manifest and Maven metadata are not.

META-INF/micronaut/**

The Micronaut bean metadata of the application and of every dependency, merged and de-duplicated, with explicit directory entries. See Micronaut service discovery.

MICRONAUT-INF/classes/

An explicit directory entry for the application layer, so that the CodeSource location of every application class names something the archive really carries and can be opened.

MICRONAUT-INF/classes/**

The application’s own classes and resources, stored exploded. This is "jar 0"; an entry’s logical name is its path with this prefix removed. Directories inside the layer are not stored; the index carries a synthetic record for each one instead.

MICRONAUT-INF/lib/<name>.jar

The dependencies, in classpath order, each a complete JAR.

By default each dependency is re-packed so that its own entries are STORED too, which removes decompression from class loading at the cost of a larger archive. Re-packing also drops signature files (META-INF/.SF, .DSA, .RSA, .EC, META-INF/SIG-*) and META-INF/INDEX.LIST. Manifests are never rewritten, so package metadata and sealing survive intact. The PRESERVE option copies each dependency byte for byte instead.

The index

MICRONAUT-INF/index.bin is a little-endian binary structure designed to be used directly from the memory mapping, with bounds checks but no parsing into objects. It consists of a fixed 128-byte header followed by five sections: a jar table, a package table, an entry table, a hash table and a string table. The exact byte layout is defined, as compile-time constants with documentation, in IndexFormat in the micronaut-runner-launcher artifact, which is the authoritative description.

The parts worth understanding:

Entry records

One per entry, per jar, carrying the entry’s absolute offset in the outer file, its sizes, CRC-32, compression method and MS-DOS timestamp. Records for one jar are contiguous, with the physical entries first in their original central directory order, so JarFile.entries() can report them faithfully.

Hash table

Maps a logical name to the first record with that name, using open addressing and linear probing. The maximum probe length actually needed is recorded at build time and validated when the index is opened, so a lookup has a hard bound.

Same-name chains

Entries that share a logical name are linked in classpath order, so getResource returns the first and getResources walks the chain, emitting one URL per contributing JAR.

Multi-release aliases

For a JAR declaring Multi-Release: true, each META-INF/versions/N/<path> entry is indexed a second time under <path>, marked with its version. Aliases precede the base entry in descending version order, so resolution takes the first record the running JDK accepts. The rule for what counts as a version directory is java.util.jar.JarFile’s, so that a JAR resolves to the same bytes inside a runner JAR as it does on an ordinary class path: `N must start with 1-9, so META-INF/versions/09/ is an ordinary entry and is never selected; N is considered from 8 upwards, and only when the effective runtime version is above 8, so a versioned entry is ignored altogether when jdk.util.jar.enableMultiRelease is false or jdk.util.jar.version selects 8; and paths that themselves start with META-INF/ are never aliased.

Package table

The per-package Name: sections of each dependency’s manifest, which override the manifest’s main attributes attribute by attribute when a package is defined.

Detecting a stale archive

The index stores the outer file’s length, and every jar record stores the offset of the local file header that introduces it. Both are checked, the second lazily per JAR, and a mismatch fails with a message telling you to rebuild. This detects an archive that was appended to, truncated or re-zipped after packaging, which would otherwise mean reading from wrong offsets. It is a staleness check, not an integrity check: it is not designed to detect deliberate tampering, and a modification that preserves the length and the header positions passes it. Full CRC verification on every read is available with -Dmicronaut.runner.verify=true.

Micronaut service discovery

Micronaut locates beans by calling getResources("META-INF/micronaut/") and then listing the directory that each returned URL denotes. Listing a directory is not something a URL can do generically, so the framework opens the archive behind the URL. For a JAR nested inside another JAR it has to mount a ZIP file system over a ZIP file system, and the JDK implements that by reading the whole inner archive into memory. Doing this once per dependency would dominate startup.

Micronaut Runner avoids it by merging that metadata at build time. Every META-INF/micronaut/<service>/<name> entry from the application and from every dependency is written, de-duplicated and in classpath order, into META-INF/micronaut/ at the root of the outer archive, with real directory entries. The class loader resolves any name under that prefix against the merged copy alone, so getResources("META-INF/micronaut/") returns exactly one URL and Micronaut lists it in a single pass over an archive the JVM already has open.

Almost all of these entries are empty markers whose name carries the information, but one that has content keeps it: the merged copy is written with the bytes of the first contributor in classpath order, and a build warns when two JARs contribute the same name with different content. Since every lookup under the prefix is answered from the merged copy, the alternative would be serving an empty stream for a file that is not empty.

Classic META-INF/services/ files are left exactly where they are, one per dependency: they are read as files through their URL, which works per JAR without any special handling.

4 Running a Runner JAR

A runner JAR is an ordinary executable JAR. Everything below is optional tuning and diagnostics.

java -jar build/libs/my-app-0.1-all.jar

Arguments after the JAR are passed to your application untouched, and an exception thrown by your application propagates exactly as it would from an ordinary main class: the JVM prints the stack trace and exits with status 1. The launcher never wraps it.

The main method is chosen the way the java launcher chooses it, JEP 512 included: main(String[]) is preferred over main(), the whole hierarchy - superclasses and the interfaces they implement - is searched for the first form before the second is considered, a main inherited as an interface default method counts, and a non-static one is invoked on a new instance built from a non-private no-argument constructor.

System properties

Property Default Effect

micronaut.runner.mode

run

run starts the application. inspect prints the index header and jar table, list prints the entries, and extract writes an exploded copy. The non-run modes consume the remaining command line arguments.

micronaut.runner.timing

false

Prints the time reached by each startup phase to standard error: archive opened, index read, class loader ready, application entered. Use it to separate launcher cost from framework cost.

micronaut.runner.mmap

true

Set to false to read the archive with positional file reads instead of a memory mapping. Slower, and only needed on a platform or file system where mapping is unavailable or undesirable.

micronaut.runner.verify

false

Set to true to verify every entry’s CRC-32 as it is read. Useful when you suspect a corrupted archive.

micronaut.runner.parent

platform

The parent of the application class loader. platform isolates the application from anything on the real java.class.path. system is an escape hatch for an agent or tool that must share types with the application.

Exit codes

Code Meaning

0

Normal termination.

1

The application threw. The JVM’s default handler printed it.

2

The launcher could not start: the archive could not be located, it was modified after packaging, or its format version is not supported.

Running from an exploded layout

extract writes the archive out as a directory: the dependencies as real JAR files under lib/, and the application classes in a JAR whose manifest names your main class and lists those dependencies in its Class-Path.

java -Dmicronaut.runner.mode=extract -jar my-app-0.1-all.jar --destination ./app
java -jar ./app/my-app.jar

The extracted form runs entirely on the JDK’s own application class loader, with no custom class loader anywhere. That matters for the JDK’s ahead-of-time cache: as described in [cdsAndAot], classes loaded by a user-defined class loader cannot be AOT-linked, so an application that will be started thousands of times in the same container image may be better served by extracting once at image build time.

Publication and replacement

Extraction stages the complete layout in a temporary sibling directory before publishing it. Without --force, the destination is checked again after staging and the final move does not replace an existing path. If another process populates the destination while extraction is running, extraction fails and preserves that occupant.

With --force, existing output is renamed to a temporary sibling backup before the staged layout is moved into place. A publication failure restores the backup when possible. If restoration or cleanup also fails, the error names the backup (or the part of it cleanup could not remove). A failed restoration therefore leaves the old output recoverable instead of silently losing it. Successful replacement removes the backup.

Forced backup, publication, and restoration first request an atomic filesystem move and fall back to an ordinary same-filesystem move only when atomic moves are unsupported. Java’s portable filesystem API does not provide an atomic directory exchange or bind earlier path-identity checks to a later move. Consequently, publishing over an existing empty destination or performing a forced replacement can briefly leave the destination absent. Forced replacement is rollback-protected but not universally transactional, and a process able to rewrite destination path components can still race publication. Keep the source and destination parent writable only by trusted participants.

5 Compatibility and Limitations

The goal is that an application behaves identically whether it runs from a runner JAR or from an ordinary classpath. The class loader is tested differentially against java.net.URLClassLoader over the same set of JARs, comparing resource resolution, resource ordering, class bytes, package attributes and code sources.

What behaves exactly as on a classpath

  • getResource returns the first match in classpath order; getResources returns one URL per contributing JAR, in classpath order, with the first element equal to what getResource returned.

  • Duplicate resources in different dependencies stay distinct, including two entries of one dependency that share a name, which stay two records.

  • A directory resolves whether or not the name ends with a slash, as ZipFile.getEntry resolves one.

  • A manifest attribute that is present but empty is reported as "" on the Package, not as absent.

  • Multi-release JARs resolve per JAR against the running JDK’s feature version, honouring jdk.util.jar.enableMultiRelease and jdk.util.jar.version. Paths under META-INF/ are never versioned.

  • Each dependency keeps its own manifest, so Package.getImplementationVersion() and the other specification and implementation attributes are correct per package, including per-package Name: sections that override the main attributes.

  • Sealed packages are enforced: loading a class into an already sealed package from a different JAR, or sealing a package that is already open, raises SecurityException.

  • Every class has a ProtectionDomain whose CodeSource location identifies the JAR it came from.

  • Resources resolve through ordinary jar:file: URLs, so URL.openStream(), URLConnection metadata and JarURLConnection.getJarFile() all work, which is what libraries that scan the classpath rely on.

Known limitations

Nested JarFile reporting

JarFile.isMultiRelease() and JarFile.getVersion() are final in the JDK and report the archive passed to the constructor, which is the outer one. A JarFile obtained for a nested dependency therefore reports the outer archive’s state from those two methods. Entry lookup still applies the nested JAR’s own multi-release policy, so resolution is correct; only these two reporting methods cannot be corrected.

Classes in io.micronaut.runner

The launcher’s own classes are loaded from the launcher, so an application or dependency class whose binary name is one of theirs - io.micronaut.runner.Index, say - resolves to the launcher’s copy. Any other class under that package prefix is loaded from the archive like any other application class.

The system class loader

Only the thread context class loader is the runner class loader. ClassLoader.getSystemClassLoader() still sees the real java.class.path, which contains only the runner JAR itself. Code that resolves classes through the system class loader, or that parses java.class.path to discover the application’s dependencies, will not find them. Micronaut resolves its application class loader from the thread context class loader, so the framework is unaffected.

Signatures are not verified

Re-packing removes signature files, and nothing is verified at run time. Sign the outer archive if you need a signature. Code that depends on CodeSource.getCodeSigners() being populated, such as a JCE provider requiring a signed JAR, is not supported.

The Java Platform Module System

Everything runs in the unnamed module of the runner class loader. A dependency’s module-info.class is carried but is inert, and modules added with --module-path are not visible to the application.

Dependency Class-Path manifest attributes

Ignored, with a warning at packaging time. They point at sibling files that do not exist inside an archive. They become active again after extract.

Native libraries

Libraries that ship native code, such as Netty’s transports, unpack it to a temporary directory themselves, exactly as they do from any JAR. Micronaut Runner does not extract anything, but it does not prevent a library from doing so.

6 Class Data Sharing and the AOT Cache

Modern JVMs can cache the work of loading and linking classes between runs. Understanding how that interacts with a runner JAR matters if startup time is your reason for being here.

The constraint

JEP 483, which introduced the AOT cache in JDK 24, is explicit:

Only classes loaded from the class path, the module path, and the JDK itself, by the JDK’s built-in class loaders, can be cached.

A runner JAR loads application classes through its own class loader, so those classes cannot be AOT-linked. This is not specific to Micronaut Runner: it applies to every executable-JAR format that keeps its dependencies nested, and it is why Quarkus added a separate packaging mode whose class loading is delegated entirely to the JDK.

What still applies is the older Class Data Sharing machinery. HotSpot archives classes defined by a user-defined class loader as unregistered classes, and when such a loader later defines a class whose name, class file size and CRC-32 match an archived one, the pre-parsed and pre-verified copy is used instead of parsing the bytes again. So an archive is still worth creating; it simply does not carry the full benefit that AOT linking gives an ordinary classpath.

Two options

Keep the single JAR. Create a CDS archive in the usual way. The same command must be used for the training run and for production:

java -XX:+AutoCreateSharedArchive -XX:SharedArchiveFile=app.jsa -jar my-app-0.1-all.jar

-XX:+AutoCreateSharedArchive requires -XX:SharedArchiveFile; it creates the archive when it is missing or stale and reuses it otherwise.

Extract once, then get everything. If the image is built once and started many times, extract at image build time and run from the exploded layout, which uses no custom class loader at all and is therefore fully AOT-linkable:

java -Dmicronaut.runner.mode=extract -jar my-app-0.1-all.jar --destination ./app
java -XX:AOTCacheOutput=app.aot -jar ./app/my-app.jar     # training run
java -XX:AOTCache=app.aot -jar ./app/my-app.jar           # production

HotSpot reads the Class-Path manifest attribute of the extracted application JAR and records every JAR it names, validating each by file size and modification time, so the whole dependency set is covered.

Verifying that it worked

Do not assume an archive is being used. Check that your own classes are coming from it:

java -XX:AOTCache=app.aot -Xlog:class+load -jar ./app/my-app.jar | grep 'shared objects file' | grep com.example

-Xlog:class+path=info reports how the recorded class path was validated, which is the first thing to look at when a cache is silently ignored.

Measure before committing to either option. The cost and benefit depend on the size of the application and on how often the process starts, and the numbers move between JDK releases.

7 Benchmarks

Performance claims about startup are easy to make and easy to get wrong, so the numbers for Micronaut Runner are produced by a harness in the repository rather than quoted from memory.

What is measured

Micro-benchmarks

JMH benchmarks over the class loader’s hot path: index lookup hit and miss, class loading against URLClassLoader on the same set of JARs, and defining a class from a mapped buffer versus a byte array. These isolate the mechanism.

Startup

The whole process, from spawn to readiness, for the same application packaged several ways: an exploded classpath, a thin JAR with a Class-Path manifest, a shaded JAR, a runner JAR with dependencies stored and preserved, and the extracted layout, each also with a CDS archive and with a JDK 25 AOT cache.

Readiness is measured externally, as the time from process spawn to the first successful HTTP response, because that is what a user waits for and it captures class loading that happens on the first request. The framework’s own "startup completed" line is recorded separately, as a second metric rather than as a substitute.

Methodology

The harness interleaves the variants in random order rather than running each in a block, discards warm-up runs, keeps every raw sample, and reports the median, the 90th percentile and a confidence interval. Timing runs carry no diagnostic flags: -Xlog changes what is being measured, so class-load counts and cache-hit counts are collected in separate runs. Both a warm and a cold page cache are measured, because storing dependencies uncompressed trades archive size against I/O.

Run it locally with:

./gradlew :benchmarks:jmh
./gradlew :benchmarks:startupBenchmark -Pbenchmarks.iterations=20

Reports are written to benchmarks/build/reports/. In CI the benchmarks run weekly and on demand rather than on every pull request, because shared runners are too noisy to gate a build on.

The cost is size. Storing dependencies uncompressed made the archive 2.5 times larger than the shaded JAR. That trade is why PRESERVE exists, and why the cold-page-cache case is measured separately: an archive this much larger can lose on a cold start what it gains on a warm one.

Two clocks, not one

The harness reports readiness and the framework’s startup line as separate columns, and they are far apart: on the sample, roughly 410 ms against roughly 330 ms for the same run. The gap is serving the first request on a cold JVM, which readiness includes by definition and a measurement that watches the console does not.

The figures in the table above are the startup line, because that is what a careful measurement by hand produces and what most published comparisons quote. Readiness is the more honest answer to "when can this serve traffic". Neither is wrong; quoting one while implying the other is. The framework’s own reported figure is a third quantity again, the smallest of the three, because the application only starts counting once the JVM has already done most of the work.

A measurement that did not move

The launcher’s own share of startup, which -Dmicronaut.runner.timing=true reports, fell from 17.4 ms to 12.3 ms when the archive reader stopped reading through VarHandle-backed layout accessors. Total startup did not change. The most likely reason is that the work was not removed from the process, only from the launcher: the first use of a var handle initialises java.lang.invoke, and the framework initialises it moments later regardless.

The change is kept because it is strictly less work, and because it does help an application that never touches method handles at all, such as a short-lived command line tool. It is recorded here because it is the clearest example of why this module measures the whole process rather than the phase it is proud of.

8 Troubleshooting

"runner jar was modified after packaging"

The index records the archive’s length and the position of every nested JAR. One of those checks failed, which means the file changed after it was built: something appended to it, re-zipped it, or signed it in place. Rebuild the archive. If you need a signature, sign the finished archive with a tool that does not rewrite existing entries, or use the extracted layout.

A resource is not found, or the wrong one is found

Resources resolve in classpath order: the application first, then dependencies in resolution order. Check what the archive actually contains:

java -Dmicronaut.runner.mode=list -jar my-app-0.1-all.jar META-INF/services

If a library finds nothing at all, check whether it discovers resources through ClassLoader.getSystemClassLoader() or by parsing java.class.path rather than through the thread context class loader. Neither sees the application’s dependencies; see the compatibility chapter.

No beans are found, or the application context is empty

Micronaut discovers beans by listing META-INF/micronaut/. Confirm the merged directory is present and populated:

java -Dmicronaut.runner.mode=list -jar my-app-0.1-all.jar META-INF/micronaut

If it is empty, the dependencies were not processed by annotation processing at build time, which is a build configuration problem rather than a packaging one.

Startup is slower than expected

Separate the launcher from the framework before tuning anything:

java -Dmicronaut.runner.timing=true -jar my-app-0.1-all.jar

That prints when the archive was opened, when the index was read, when the class loader was ready and when your application was entered. If the time is spent after "application entered", it is the framework or the application, not the packaging.

A library fails with an unexpected URL

Resources are exposed through ordinary jar:file: URLs. A resource inside a dependency uses the nested form jar:file:/path/app.jar!/MICRONAUT-INF/lib/dep.jar!/name. Libraries that split such a URL at the first !/ rather than the last may misread it. Report it: in most cases it can be handled on our side.

An exception mentions SecurityException: sealing violation

A dependency declares a sealed package and another JAR contributes a class to the same package. That is a genuine conflict which a shaded JAR would have hidden. Resolve the duplicate dependency, or relocate one of them.
