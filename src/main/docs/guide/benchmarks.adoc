Performance claims about startup are easy to make and easy to get wrong, so the numbers for Micronaut
Runner are produced by a harness in the repository rather than quoted from memory.

== What is measured

Micro-benchmarks:: JMH benchmarks over the class loader's hot path: index lookup hit and miss, class
loading against `URLClassLoader` on the same set of JARs, and defining a class from a mapped buffer versus
a byte array. These isolate the mechanism.

Startup:: The whole process, from spawn to readiness, for the same application packaged in the eight modes
that the current harness implements:
+
[cols="25,75"]
|===
|Variant |Packaging

|`exploded-cp`
|Class files and dependency JARs on an explicit class path

|`thin-jar`
|Application JAR with a `Class-Path` manifest

|`shadow`
|One JAR flattened by the Shadow plugin

|`runner-stored`
|Runner JAR with nested dependencies re-packed uncompressed and the plugin-default entry stub

|`runner-stored-reflection`
|The same stored Runner JAR inputs with the entry stub disabled, as a reflection ablation

|`runner-preserve`
|Runner JAR with nested dependencies copied byte for byte and the plugin-default entry stub

|`runner-preserve-reflection`
|The same preserved Runner JAR inputs with the entry stub disabled, as a reflection ablation

|`runner-extracted`
|The stored Runner JAR extracted and launched by the JDK's built-in loader
|===

Each sample starts a fresh JVM. Readiness is measured externally, from process spawn to the first successful
HTTP response, because that is what a user waits for and it captures class loading on the first request. The
framework's own "startup completed" line is recorded separately rather than substituted for readiness.

None of these eight commands uses a trained application cache. Default JDK class sharing remains enabled when
the selected JDK enables it, but reuse of platform classes from the JDK's default archive is not evidence of
trained application-class CDS or AOT reuse.

== Methodology

The harness interleaves the variants in random order rather than running each in a block, discards designated
warm-up runs, keeps every raw sample, and always reports descriptive counts, medians and 90th percentiles.
Confidence intervals are omitted and the summary is labelled descriptive-only until there are at least ten
successful measured samples. Ten is a reporting threshold, not a universal guarantee of precision; a
zero-width interval over repeated observations cannot recover variability that was never observed.
Discarding a process run does not evict or warm the OS page cache in a controlled way. The OS page cache is
uncontrolled and is typically affected by the build and earlier starts; the harness has no page-cache eviction
protocol on Linux, macOS or Windows and therefore reports neither a warm-cache nor a cold-filesystem-cache
measurement.

Pairwise readiness comparisons predeclare the median iteration-level difference (left minus right) as their
estimator. Bootstrap resampling uses complete measured iteration pairs as its unit, preserving the shared
iteration conditions. A failed, missing or unavailable attempt excludes that iteration and remains visible in
the pair and exclusion counts; successful values from later iterations are never shifted into the gap. Paired
intervals use the same minimum of ten complete pairs, retain the seed and method in `results.json`, and do not
by themselves establish a startup speedup or statistical significance.

Timing runs carry no diagnostic flags: `-Xlog` changes what is being measured, so class-load counts are
collected in separate runs. Those diagnostics may show default JDK class sharing, but the current variants do
not train or select a CDS archive or an AOT cache. The harness removes `JAVA_TOOL_OPTIONS`,
`JDK_JAVA_OPTIONS` and `_JAVA_OPTIONS` from child JVM environments so ambient flags cannot silently change
that cache mode.

=== Planned trained-cache matrix

Direct Runner trained CDS is planned in
https://github.com/alvarosanchez/micronaut-runner/issues/44[#44]. Extracted-layout JDK AOT caching is planned
in https://github.com/alvarosanchez/micronaut-runner/issues/45[#45]. Both are future modes and are not
measured by the current harness. JDK AOT caching is not GraalVM Native Image, and custom-loader CDS is not
the full built-in-loader AOT-linking path.

Before those rows can be treated as measurements, they must demonstrate reuse of application classes, train
competing layouts with equivalent workloads and options, define cache invalidation inputs, and report cache
misses honestly. A cache mode unsupported by the selected JDK or platform must be reported as unavailable,
not silently run without its trained application cache.

Run it locally with:

[source,bash]
----
./gradlew :benchmarks:jmh
./gradlew :benchmarks:startupBenchmark -Pbenchmarks.iterations=20
----

Reports are written to `benchmarks/build/reports/`. In CI the benchmarks run weekly and on demand rather
than on every pull request, because shared runners are too noisy to gate a build on.

The startup harness uses a required, fail-closed matrix by default. Every required packaging variant must
be built and complete every requested measured iteration; otherwise the task exits nonzero _after_ writing
both `results.json` and `summary.md`. Both reports show requested, attempted, successful, failed and skipped
counts separately for warm-up and measured phases. `results.json` also records every process attempt with
its variant, iteration, global schedule order, phase, outcome, failure and exit information, and timing only
when the attempt produced a valid measurement. A build-unavailable variant is skipped, not mislabeled as a
failed process attempt. A warm-up failure is visible but does not by itself invalidate a complete measured
matrix.

For investigation only, `-Pbenchmarks.allowPartial=true` selects the explicit partial policy. An incomplete
partial run is labelled as such in both reports and exits zero only when at least one measured attempt
succeeds. Its timing distributions remain explicitly conditional on successful attempts; the harness never
turns a timeout into a zero duration or retries until a favorable sample appears.

The size column is the complete deployment boundary, not just the process's launch artifact. It sums the
logical lengths of every required regular file: the application and dependency components for thin and
exploded layouts, the whole extracted layout, or the single complete archive for Shadow and Runner variants.
Both reports expose component bytes and the reconciled total in bytes. Repeated normalized paths are counted
once and attributed to the first component that names them. Symbolic links are not followed or counted;
distinct hard-linked paths are counted separately. Build workspaces, logs, reports and neighboring variants
are outside the explicitly declared inputs and are never included.

== First measurements

These are the numbers from the prototype gate, taken on one developer machine (Apple silicon, JDK 25) with
the `hello-netty` sample: a Micronaut 5 application with 35 dependencies. Nine runs per variant,
interleaved rather than run in blocks, measuring from process spawn to the framework reporting that
startup completed. Treat them as a direction, not a specification; the CI harness is the authority.

[cols="30,20,25,25"]
|===
|Variant |Total |Framework-reported |Archive size

|Runner JAR, dependencies stored
|318 ms
|178 ms
|31.4 MB

|Shaded JAR
|363 ms
|202 ms
|12.8 MB

|Exploded classpath
|374 ms
|374 ms is the whole process; 201 ms reported
|n/a
|===

The descriptive medians put the runner JAR 12% below the shaded JAR and 15% below an exploded classpath in
that prototype run. With only nine observations per variant, the current harness would label those values
descriptive-only and emit no interval, so they are not evidence of a general startup speedup. The accompanying
framework-reported figures moved in the same direction, a hypothesis for follow-up rather than a significance
claim.

The measured cost was size: storing dependencies uncompressed made the archive 2.5 times larger than the
shaded JAR. That observation motivated `PRESERVE`; the prototype did not control the OS page cache, so it
did not measure whether the larger archive loses after filesystem-cache eviction.

=== Class loading in isolation

The JMH benchmarks measure the mechanism rather than the application. Over a synthetic classpath of 30
jars and 3,600 classes, loading 200 classes through a freshly created loader, including opening the
archive:

[cols="55,45"]
|===
|Loader |Time for 200 classes

|`RunnerClassLoader`, dependencies stored
|1.4 ms

|`RunnerClassLoader`, dependencies left compressed
|2.1 ms

|`URLClassLoader` over the same jars
|9.2 ms
|===

Storing dependencies uncompressed is worth about 35% of the class-loading time, which is what pays for
the larger archive. Defining a class from a memory-mapped buffer rather than a byte array is worth about
2%: on JDK 26 the virtual machine copies a direct buffer for a non-builtin loader anyway, so what is saved
is the application-side array and the copy into it, not the copy itself.

=== Archive size

[cols="55,45"]
|===
|Packaging |Size

|Runner JAR, dependencies stored
|31.4 MB

|Runner JAR, dependencies preserved
|14.1 MB

|Shaded JAR
|12.8 MB
|===

`PRESERVE` copies each dependency byte for byte, so the archive is close to the shaded one and class
loading pays for decompression. It reduces deployment size when that matters more than the measured
warm-state class-loading cost. A larger `STORED` archive may require more storage I/O after filesystem-cache
eviction, but cold-storage performance has not been measured by this harness, so these figures do not
establish a cold-start winner.

=== Two clocks, not one

The harness reports readiness and the framework's startup line as separate columns, and they are far
apart: on the sample, roughly 410 ms against roughly 330 ms for the same run. The gap is serving the first
request on a cold JVM, which readiness includes by definition and a measurement that watches the console
does not.

The figures in the table above are the startup line, because that is what a careful measurement by hand
produces and what most published comparisons quote. Readiness is the more honest answer to "when can this
serve traffic". Neither is wrong; quoting one while implying the other is. The framework's own reported
figure is a third quantity again, the smallest of the three, because the application only starts counting
once the JVM has already done most of the work.

== A measurement that did not move

The launcher's own share of startup, which `-Dmicronaut.runner.timing=true` reports, fell from 17.4 ms to
12.3 ms when the archive reader stopped reading through `VarHandle`-backed layout accessors. Total startup
did not change. The most likely reason is that the work was not removed from the process, only from the
launcher: the first use of a var handle initialises `java.lang.invoke`, and the framework initialises it
moments later regardless.

The change is kept because it is strictly less work, and because it does help an application that never
touches method handles at all, such as a short-lived command line tool. It is recorded here because it is
the clearest example of why this module measures the whole process rather than the phase it is proud of.
