Performance claims about startup are easy to make and easy to get wrong, so the numbers for Micronaut
Runner are produced by a harness in the repository rather than quoted from memory.

== What is measured

Micro-benchmarks:: JMH benchmarks over the class loader's hot path: index lookup hit and miss, package-table
lookup, class loading, defining a class from a mapped buffer versus a byte array, resource lookup and
streaming, duplicate-resource enumeration and service discovery. Named synthetic shapes vary JAR and entry
count, class size and locality, resource size, manifest packages, duplicate names and multi-release entries.
These isolate mechanisms; they are not startup results. Class loading and resource lookup are compared with
two JDK baselines built from the same synthetic inputs as the Runner archives:
+
* The `Shaded*` benchmarks run a `URLClassLoader` over one flattened JAR: the application first, then every
dependency in class-path order, with `META-INF/services` descriptors merged, first-wins duplicates and every
entry DEFLATED. This is the layout of the `shadow` startup variant, and the comparison Runner has to win.
`java -jar` runs a Shadow JAR on the JDK's built-in application class loader rather than `URLClassLoader`,
so this baseline is a proxy for it.
* The `URL*` benchmarks run a `URLClassLoader` over the application classes plus every dependency JAR. This is
the layout of the `thin-jar` and `exploded-cp` startup variants.

Packaging:: Fresh-JVM profiles build STORED and PRESERVE Runner archives for deterministic first-build,
unchanged-rebuild, application-edit and dependency-edit scenarios. Elapsed time/allocation and process
RSS/peak heap come from separate invocations. Logical input/output bytes are reported separately from time and
memory and are not kernel I/O counters.
+
`packagingComparison` packages a real application instead, a fresh copy of `test-suite/samples/benchmark-large`,
in one warm Gradle daemon of its own, which is where developers and CI pay for packaging. It compares Runner with
the Shadow JAR it replaces: `micronautRunnerJar` with STORED (`runner-stored`) and PRESERVE (`runner-preserve`)
compression against `shadowJar` (`shadow`) and the sample's STORED control `shadowJarStored` (`shadow-stored`).
The `rerun` scenario runs `<task> --rerun`, which re-executes only the packaging task; `micronautRunnerJar` keeps
no packaging state between executions, so this is the cold packaging path and there is no separate cold
scenario. The `edit` scenario makes a bytecode-changing edit to `Application.java` and runs `<task>`, so
compilation and the packaging task's other dependencies execute as well. Each invocation records the packaging
task's action time and the wall time of the whole `gradlew` process. The comparisons are `runner-stored`/`shadow`
(the defaults) and the compression-matched `runner-stored`/`shadow-stored` (neither archive deflated) and
`runner-preserve`/`shadow` (both deflated), each the median of per-round differences.
+
Maven Shade is not compared. `test-suite/samples/maven-basic` configures no `maven-shade-plugin`, and in that
small sample Maven's own startup would dominate the timings. The Maven plugin packages with the same
`runner-build` code path as the Gradle task, which the Runner rows here and `packagingProfile` already cover.

Startup:: The whole process, from spawn to readiness, for the same application packaged in each mode that the
current harness implements:
+
[cols="25,75"]
|===
|Variant |Packaging

|`exploded-cp`
|Class files and dependency JARs on an explicit class path

|`thin-jar`
|Application JAR with a `Class-Path` manifest

|`shadow`
|One JAR flattened by the Shadow plugin

|`shadow-stored`
|The same Shadow task inputs written with `entryCompression = ZipEntryCompression.STORED`, a compression-matched
control

|`shadow-aot`
|The identical Shadow JAR with a trained, application-class-verified JDK AOT cache

|`runner-stored`
|Runner JAR with nested dependencies re-packed uncompressed and the plugin-default entry stub

|`runner-stored-aot`
|The identical default-entry stored Runner JAR with a trained, application-class-verified JDK AOT cache

|`runner-stored-reflection`
|Opt-in, non-gating ablation: the same stored Runner JAR inputs with the entry stub disabled, which measures the
plugin-default entry stub against reflective entry

|`runner-preserve`
|Runner JAR with nested dependencies copied byte for byte and the plugin-default entry stub

|`runner-extracted`
|The stored Runner JAR extracted and launched by the JDK's built-in loader

|`runner-extracted-aot`
|The identical extracted layout and manifest class path with a trained, application-class-verified JDK AOT
cache
|===

Each sample starts a fresh JVM. This is a cold JVM process start, not a claim that storage or the OS page cache
is cold. Readiness is measured externally, from process spawn to the first successful HTTP response, because
that is what a user waits for and it captures class loading on the first request. The framework's own "startup
completed" line is recorded separately rather than substituted for readiness.

The cache pairs are `runner-stored`/`runner-stored-aot`, `shadow`/`shadow-aot`, and
`runner-extracted`/`runner-extracted-aot`. Each pair shares the exact artifact bytes, ordered class path,
working directory, measured workload and JVM options except for the one application-cache selection option.
Default JDK class sharing remains enabled when the selected JDK enables it, but reuse of platform classes from
the JDK's default archive is not evidence of trained application-class AOT cache reuse; default JDK class
sharing is a separate baseline condition.

The compression-matched pairs are `runner-stored`/`shadow-stored`, where neither side inflates class bytes, and
`runner-preserve`/`shadow`, where both do; they measure what Runner's layout itself buys. `runner-stored`/`shadow`
is the default-vs-default pair, and its difference also includes the cost of inflating Shadow's DEFLATED entries.

== Methodology

The harness interleaves the variants in random order rather than running each in a block, discards designated
warm-up runs, keeps every raw sample, and always reports descriptive counts, medians and 90th percentiles.
Confidence intervals are omitted and the summary is labelled descriptive-only until there are at least ten
successful measured samples. Ten is a reporting threshold, not a universal guarantee of precision; a
zero-width interval over repeated observations cannot recover variability that was never observed.
Discarding a process run does not evict or warm the OS page cache in a controlled way. The OS page cache is
uncontrolled and is typically affected by the build and earlier starts; the harness has no page-cache eviction
protocol on Linux, macOS or Windows and therefore reports neither a warm-cache nor a cold-filesystem-cache
measurement.

Readiness comparisons are a predeclared list of candidate minus baseline pairs, led by `runner-stored` minus
`shadow`, so a negative difference means the candidate is faster. Each reports the median per-iteration
difference and a relative change, the median per-iteration candidate/baseline ratio minus one, over complete
measured iterations only; an incomplete iteration is excluded and listed, never re-paired. A bootstrap interval
over complete iteration pairs appears only with at least ten complete pairs.

Timing runs carry no diagnostic flags: `-Xlog` changes what is being measured, so class counts are read
without it. Before timing begins, each cache lifecycle makes its own diagnostic launch and
requires `com.example.Application`, an application class, to load from the selected shared objects file;
aggregate shared-class counts alone are insufficient. The harness removes `JAVA_TOOL_OPTIONS`,
`JDK_JAVA_OPTIONS`, `_JAVA_OPTIONS` and `JDK_AOT_VM_OPTIONS` from child JVM environments so ambient flags
cannot silently change that cache mode.

Every successful timing run also records memory and loaded classes once, after HTTP readiness and outside the
timed interval: `atReadiness` in `results.json`, per attempt and as per-variant medians, and the summary's
memory table. Memory is read in-process, from `/proc/<pid>/status` on Linux (`VmRSS`, `VmHWM`, `RssAnon`,
`RssFile`) and from `proc_pid_rusage` on macOS (resident size, `phys_footprint` and its lifetime peak). Class
counts come from one `jstat -snap` of the child's JDK, which reads its performance counters without attaching and
adds no flag to the child. A value that cannot be read is `null`: all of them on Windows, and the class counts of
a JVM started with `-XX:-UsePerfData`. RSS includes clean, file-backed pages of memory-mapped files (the Runner
archive, CDS and AOT archives, JDK libraries) that the kernel can drop and re-read, so private memory
(`phys_footprint` or `RssAnon`) is the like-for-like comparison between a mapped archive and a flattened JAR. The
`-Xlog` files that `-Pbenchmarks.diagnostics=true` writes still cover spawn through shutdown and are for per-class
inspection; their readiness only shows the logging overhead and never enters measured timing distributions.

=== Trained-cache matrix

All three cache pairs, `runner-stored`/`runner-stored-aot`, `shadow`/`shadow-aot` and
`runner-extracted`/`runner-extracted-aot`, use the JDK AOT cache, so a trained Runner layout is never compared
only with an untrained Shadow layout. Classes that Runner's loader defines are cached but not AOT-linked. JDK AOT
caching is not GraalVM Native Image.

Training and verification are bounded build-time operations outside all timing samples. Training reaches
HTTP readiness, exercises `/hello`, sends SIGTERM for an orderly shutdown, accepts exit status 0 or 143, requires a
nonempty cache, then performs a strict diagnostic launch. The managed cache identity hashes the immutable
final JAR (and therefore its embedded application and dependency bytes), exact JDK/VM build, architecture,
launch options and workload paths. A changed input selects a different cache. A cached variant is measured only
after a nonempty completed cache and a successful application-class verification launch; an unsupported JDK or
any failed phase makes the variant unavailable, and the benchmark never silently substitutes a no-cache process.
The launch cannot start without the trained cache file, so its bytes count toward the complete deployment;
training cost and total preparation cost are reported separately from deployment bytes and readiness
measurements. The cached variants require JDK 25 or later: training
uses `-XX:AOTCacheOutput=<cache>` and measured use adds `-XX:AOTMode=on -XX:AOTCache=<cache>`, so a missing or
unusable cache fails the launch. They launch the actual Shadow JAR, Runner JAR or extracted application JAR,
with no helper or wrapper added to either paired class path. See <<cdsAndAot>> for the reproducible extraction
and deployment workflow. These three rows make the trained application cache mode explicit rather than
inferring it from default JDK class sharing.

Run it locally with:

[source,bash]
----
./gradlew :benchmarks:jmh
./gradlew :benchmarks:packagingProfile
./gradlew :benchmarks:packagingComparison
./gradlew :benchmarks:startupBenchmark -Pbenchmarks.iterations=20
./gradlew :benchmarks:startupBenchmark -Pbenchmarks.iterations=1 -Pbenchmarks.diagnostics=true
./gradlew :benchmarks:startupBenchmark -Pbenchmarks.optionalRows=true -Pbenchmarks.iterations=40
----

The last command adds the opt-in rows, such as the entry-stub ablation. Run it with 40 iterations: at 20, the
stub effect's interval still spanned zero.

`-Pbenchmarks.workloads=no-manifest,small,representative,wide` selects packaging shapes and
`-Pbenchmarks.packagingIterations=2` changes the number of independent packaging workers. The JMH resource
benchmarks expose the same `workload` parameter. The startup task defaults to the larger
`test-suite/samples/benchmark-large` application; use `-Pbenchmarks.sample=<sample-directory-name>` for an
explicit sample. Short smoke runs must remain labelled descriptive rather than being promoted to release
claims.

`packagingComparison` always uses `benchmark-large` and ignores `-Pbenchmarks.sample`. It runs 3 warm-up rounds
and then 10 measured rounds, the fewest that give a 95% interval; `-Pbenchmarks.packagingComparisonIterations=20`
changes the measured count. Each round runs one untimed `classes` build, then every variant in the `rerun`
scenario and then in the `edit` scenario, each scenario in a fresh order shuffled from a seed that the report
records. Its nested builds run with `--no-build-cache --no-configuration-cache` in a daemon that its unique JVM
options keep apart from every other daemon and that stops itself 60 seconds after the task ends; the harness
never runs `--stop`.

Reports are written to `benchmarks/build/reports/`. The startup task builds its variants and trains its caches
in `benchmarks/build/tmp/startupBenchmark`, and the packaging comparison builds its copy of the sample in
`benchmarks/build/tmp/packagingComparison`. In CI the benchmarks run weekly and on demand rather than on every
pull request, because shared runners are too noisy to gate a build on.

The startup harness uses a required, fail-closed matrix by default. Every required packaging variant must
be built and complete every requested measured iteration; otherwise the task exits nonzero _after_ writing
both `results.json` and `summary.md`. Both reports show requested, attempted, successful, failed and skipped
counts separately for warm-up and measured phases. `results.json` also records every process attempt with
its variant, iteration, global schedule order, phase, outcome, failure and exit information, and timing only
when the attempt produced a valid measurement. A build-unavailable variant is skipped, not mislabeled as a
failed process attempt. A warm-up failure is visible but does not by itself invalidate a complete measured
matrix. Opt-in rows are built only with `-Pbenchmarks.optionalRows=true`, and their failures are reported but
never change the exit code.

`results.json` uses a versioned, relocatable provenance schema. It records runner and sample revisions plus
clean/dirty state, exact JDK and platform identity, logical processor count and physical memory, cache policy,
the seed and actual attempt order, relocatable effective command arrays, and SHA-256 identities for ordered
launch inputs. The four ambient JVM-option variables (`JAVA_TOOL_OPTIONS`, `JDK_JAVA_OPTIONS`, `_JAVA_OPTIONS` and
`JDK_AOT_VM_OPTIONS`) are recorded only as present/absent and removed; their values are explicitly redacted. Full
environments, repository locations, Java homes and private absolute paths are never serialized. A reader can therefore identify the exact launched bytes and reconstruct successes and
failures without depending on the original checkout location.

For investigation only, `-Pbenchmarks.allowPartial=true` selects the explicit partial policy. An incomplete
partial run is labelled as such in both reports and exits zero only when at least one measured attempt
succeeds. Its timing distributions remain explicitly conditional on successful attempts; the harness never
turns a timeout into a zero duration or retries until a favorable sample appears.

The size column is the complete deployment boundary, not just the process's launch artifact. It sums the
logical lengths of every required regular file: the application and dependency components for thin and
exploded layouts, the whole extracted layout, or the single complete archive for Shadow and Runner variants,
plus the trained cache file for every cached variant. Both reports give two metrics for each component and for
the reconciled total: raw logical bytes, and gzip -6 bytes, the sum of per-file gzip -6 lengths, an
approximation of image-layer transfer size (tar headers and cross-file dictionary effects excluded). The gzip
lengths are computed while variants are prepared, never during timed launches. Repeated normalized paths are
counted once and attributed to the first component that names them. Symbolic links are not followed or
counted, except that a required cache file which is a link is an error; distinct hard-linked paths are counted
separately. Build workspaces, logs, reports and neighboring variants are outside the explicitly declared inputs
and are never included. STORED stays the default and no resources-only deflate mode is planned: STORED's raw
archive is the larger one, but classes are about 94% of the benchmark sample's uncompressed content, so
compressing only resources could not close that gap.

== Publishing results

This guide does not retain the early prototype numbers because their raw samples and complete executable
configuration were not archived publicly. They cannot substantiate a current speedup claim. In particular,
allocation avoided by defining from a mapped buffer must not be restated as elapsed-time savings, and
cold-storage performance has not been measured by this harness.

A publishable result must link to an immutable source revision and the raw `results.json` and `summary.md`
produced by that revision. It must identify the machine and operating system, exact JDK build, sample and
dependency set, packaging variant, benchmark command and properties, warm-up and measured counts, timeout,
and application-cache and OS-page-cache conditions. Startup numbers must say whether the metric is external
process-to-HTTP-readiness, process-to-startup-line, or framework-reported self-time.

Attributing a difference to stored dependencies, merged discovery, mapped-buffer definition or another
mechanism additionally requires a matched ablation that changes only that mechanism. Hash-collision,
resource-resolution and merged-metadata fixtures validate behavior; they cannot prove a performance cause.
Until a report meeting these requirements is archived at an immutable public URL, run the harness for the
environment of interest and treat its output as local descriptive evidence rather than a published result.
