For ordinary resources, the goal is that an application behaves identically whether it runs from a runner
JAR or from an ordinary classpath. The class loader is tested differentially against
`java.net.URLClassLoader` over the same set of JARs, comparing resource resolution, resource ordering, class
bytes, package attributes and code sources. The deliberate `META-INF/micronaut/` metadata-tree exception and the
known limitations below bound that compatibility contract; they are not ordinary-classpath behavior.

== What behaves exactly as on a classpath

* `getResource` returns the first match in classpath order; `getResources` returns one URL per contributing
JAR, in classpath order, with the first element equal to what `getResource` returned.
* Duplicate resources in different dependencies stay distinct, including two entries of one dependency
that share a name, which stay two records.
* A directory resolves whether or not the name ends with a slash, as `ZipFile.getEntry` resolves one.
* A manifest attribute that is present but empty is reported as `""` on the `Package`, not as absent.
* Multi-release JARs resolve per JAR against the running JDK's feature version, honouring
`jdk.util.jar.enableMultiRelease` and `jdk.util.jar.version`. Paths under `META-INF/` are never versioned.
* Each dependency keeps its own manifest, so `Package.getImplementationVersion()` and the other
specification and implementation attributes are correct per package, including per-package `Name:`
sections that override the main attributes.
* Sealed packages are enforced: loading a class into an already sealed package from a different JAR, or
sealing a package that is already open, raises `SecurityException`.
* Every class has a `ProtectionDomain` whose `CodeSource` location identifies the JAR it came from.
* Resources resolve through ordinary `jar:file:` URLs, so `URL.openStream()`, `URLConnection` metadata and
`JarURLConnection.getJarFile()` all work, which is what libraries that scan the classpath rely on.

== Deliberate Micronaut metadata exception

Micronaut Runner merges every entry below `META-INF/micronaut/` from the application and its dependencies into
one de-duplicated tree at the outer archive root. A lookup anywhere under that prefix uses only the merged
tree, and `getResources("META-INF/micronaut/")` returns one merged URL rather than one URL per contributing
JAR. When contributors provide the same file name, the first content in classpath order is retained and a
warning reports differing later content. This is intentional build-time aggregation for Micronaut bean
discovery, not ordinary resource enumeration. Classic `META-INF/services/**` resources are not merged and
keep the classpath behavior described above.

== Archive path URLs

The outer archive's `file:` URL has one canonical representation. File-system separators are `/` over the
complete URL path, including components after Unicode text. Unicode is encoded as UTF-8 bytes, and spaces,
`%`, `#` and `?` are percent-encoded. A Windows drive path therefore starts with `file:/C:/`; a UNC shape
starts with `file://server/share/`. On POSIX, a backslash is data rather than a separator and is encoded as
`%5C`.

Windows CI starts both the synthetic end-to-end fixture and a real Micronaut HTTP application from a path
shaped like `unicode-é/apps with a space/app.jar`. The former opens resources through `URL`, `JarFile` and
the same URI-to-`File` conversion that Micronaut uses to list bean metadata; the latter must start and find
its beans before serving a request. A separate Windows JDK 25 regression probe confirms that the previous
non-canonical representation, which changed later separators to `%5C`, was still accepted by `File`,
`URL.openStream()`, `JarFile` and a `jar:` URL. The encoding defect therefore did not reproduce as a startup
or bean-discovery failure in those supported consumers. Hosted CI has no network share, so UNC behavior is
limited to deterministic URL-shape coverage rather than opening a real UNC archive.

== Known limitations

Nested `JarFile` reporting:: `JarFile.isMultiRelease()` and `JarFile.getVersion()` are `final` in the JDK
and report the archive passed to the constructor, which is the outer one. A `JarFile` obtained for a
nested dependency therefore reports the outer archive's state from those two methods. Entry _lookup_ and
`versionedStream()` still apply the nested JAR's own multi-release policy, so both resolution and effective
enumeration are correct; only these two reporting methods cannot be corrected.

Classes in `io.micronaut.runner`:: The launcher's own classes are loaded from the launcher, so an
application or dependency class whose binary name is one of theirs - `io.micronaut.runner.Index`, say -
resolves to the launcher's copy. Any other class under that package prefix is loaded from the archive like
any other application class.

The system class loader:: Only the thread context class loader is the runner class loader.
`ClassLoader.getSystemClassLoader()` still sees the real `java.class.path`, which contains only the runner
JAR itself. Code that resolves classes through the system class loader, or that parses `java.class.path`
to discover the application's dependencies, will not find them. Micronaut resolves its application class
loader from the thread context class loader, so the framework is unaffected.

Signatures are not verified:: The default re-packing mode removes nested signature files. `PRESERVE` keeps
the nested JAR bytes, including signature files, but the runner still does not verify them. Application and
dependency `CodeSource` objects have a null `CodeSigner[]`. External authentication of the outer artifact
does not change that, so code that requires signed-JAR semantics, such as a signed JCE provider, is not
supported. See <<authenticating>> for deployment-artifact authentication.

The Java Platform Module System:: Everything runs in the unnamed module of the runner class loader. A
dependency's `module-info.class` is carried but is inert, and modules added with `--module-path` are not
visible to the application.

Dependency `Class-Path` manifest attributes:: Ignored, with a warning at packaging time. They point at
sibling files that do not exist inside an archive. They become active again after `extract`.

Native libraries:: Libraries that ship native code, such as Netty's transports, unpack it to a temporary
directory themselves, exactly as they do from any JAR. Micronaut Runner does not extract anything, but it does
not prevent a library from doing so.

[[authenticating]]
== Authenticating a deployment artifact

Do not run `jarsigner`, edit the manifest, re-zip or append to the runner JAR after packaging: the launcher
rejects the rewritten file, whose length and entry offsets no longer match its index. To authenticate the JAR,
sign the finished file externally, for example with a detached signature, and verify it against a pinned key
before launch: `gpg --verify app.jar.asc app.jar && exec java -jar app.jar`. The runner still does not verify
nested JAR signatures (see _Signatures are not verified_ above), and `-Dmicronaut.runner.verify=true` CRC
checks detect corruption, not authorship. See <<archiveLifetime,archive lifetime>>.
