An application behaves in a Runner JAR as it does on an ordinary class path, with the exceptions on this page.

== What behaves as on a class path

* `getResource` returns the first match in class path order, and `getResources` one URL per JAR that has the
resource, in the same order.
* Duplicate resources in different dependencies stay distinct.
* Each dependency keeps its manifest, so `Package.getImplementationVersion()` and the other package attributes are
correct per JAR, and sealed packages are enforced.
* Multi-release JARs resolve per JAR against the running JDK.
* Resources have ordinary `jar:file:` URLs, so `URL.openStream()` and `JarURLConnection` work, as libraries that scan
the class path expect.
* Every class's `CodeSource` names the JAR it came from.

== Micronaut's metadata is merged

Micronaut finds its beans by listing the `META-INF/micronaut/` directory of each JAR on the class path, which for
JARs nested in another JAR would mean opening every one of them at startup. So Runner merges that directory from your
application and every dependency into one, at the root of the archive, and Micronaut reads it in one pass.
`getResources("META-INF/micronaut/")` therefore returns one URL, not one per JAR. When two JARs ship the same file
with different content, the first in class path order wins, and the build warns. `META-INF/services/` files are not
merged.

== Known limitations

Libraries that use the system class loader:: Runner's class loader loads your application and its dependencies, and
is also the thread context class loader. Micronaut loads classes and services through it, so Micronaut is not
affected, and neither is a library that uses the context class loader or its own classes' loader. In the single JAR,
`ClassLoader.getSystemClassLoader()` sees only the Runner JAR itself, so a library that loads a dependency's class
through it does not find the class. The same holds for the JDK's own lookups through that loader, such as security
providers listed in the `java.security` file, file system providers for `Path.of(URI)`, and `java.util.logging`
handlers named in `logging.properties`. All of them work in an <<extract,extracted layout>>, whose class path holds
every dependency. In the single JAR, a security provider can instead be registered in code, with
`Security.addProvider`.
Libraries that read `java.class.path`:: In the single JAR, the property names only the Runner JAR, in which your
dependencies are nested JARs, so a library that finds classes by scanning the files it names does not find theirs. In
an <<extract,extracted layout>>, it names only the application JAR, as for any JAR started with `java -jar`, and that
JAR's manifest lists the dependencies in its `Class-Path`. Micronaut does not use the property.
Signed dependencies:: Runner does not verify the signatures of the JARs nested in the single JAR, and their classes
have no code signers. That matters only to code that requires verified signatures. The common case is a signed JCE
provider, such as Bouncy Castle, on Oracle JDK, which enforces JCE provider signing; OpenJDK builds do not check it,
so there the provider works from the single JAR. Where signatures are checked, such code works only in an
<<extract,extracted layout>> of a Runner JAR packaged with `PRESERVE` (<<compression,Compression Modes>>), which keeps
the signed JARs byte for byte; the JDK's own class loader then verifies them. `STORED` and `HYBRID` remove the
signature files when they package, so their extracted layouts hold no signed JARs. The build warns about every signed
dependency.
The module path:: Everything runs in one unnamed module, as on a class path. A dependency's `module-info.class` is
ignored, and modules added with `--module-path` are not visible to your application.
A dependency's `Class-Path` attribute:: Ignored, with a warning when the archive is packaged, because the files it
names are not in the archive. It applies again in an extracted layout.
Native libraries:: Libraries that ship native code, such as Netty's native transports, unpack it to a temporary
directory themselves, as from any JAR. That directory must be writable.
Relocation:: Runner never renames packages. A build that relies on Shadow relocation to separate two versions of a
library needs another solution.

The launcher uses only the `java.base` module, so a `jlink` runtime needs only the modules your application needs.

[[javaAgents]]
== Java agents

An agent started with `-javaagent`, such as a monitoring or tracing agent, sees every class Runner defines and can
transform it, as with any class loader. The agent itself is loaded by the system class loader, which your
application does not see by default. An agent that puts the classes it shares with your application on the boot
class path needs nothing more.

Start with `-Dmicronaut.runner.parent=system` when your application must see the agent's classes from the class
path, or when the agent adds JARs to the class path at run time. The application's class loader then delegates to the
system class loader, and Runner turns off the <<staticServices,precomputed service lookups>>, so that Micronaut also
finds services on the real class path.

An agent attached to a running JVM, rather than started with `-javaagent`, sees the classes of a
<<startupProfile,startup profile>> as already loaded.

Runner's tests do not cover a particular monitoring agent, such as the OpenTelemetry, Datadog or New Relic Java
agent. If one misbehaves in a Runner JAR, please https://github.com/{githubSlug}/issues[report it].

[[authenticating]]
== Authenticating a deployment artifact

Do not run `jarsigner` on a Runner JAR, or change it in any other way after packaging
(<<archiveLifetime,Archive Lifetime>>). To prove where an archive comes from, sign the finished file externally and
verify it before you start it, for example:

[source,bash]
----
gpg --verify my-app-0.1-all.jar.asc my-app-0.1-all.jar && exec java -jar my-app-0.1-all.jar
----

`-Dmicronaut.runner.verify=true` detects a corrupted archive, not who built it.
