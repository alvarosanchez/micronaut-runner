A runner JAR is an ordinary executable JAR. Everything below is optional tuning and diagnostics.

[source,bash]
----
java -jar build/libs/my-app-0.1-all.jar
----

Arguments after the JAR are passed to your application untouched, and an exception thrown by your
application propagates exactly as it would from an ordinary main class: the JVM prints the stack trace and
exits with status 1. The launcher never wraps it.

The main method is chosen the way the `java` launcher chooses it, JEP 512 included: `main(String[])` is
preferred over `main()`, the whole hierarchy - superclasses and the interfaces they implement - is searched
for the first form before the second is considered, a `main` inherited as an interface default method
counts, and a non-static one is invoked on a new instance built from a non-private no-argument
constructor.

== System properties

[cols="30,15,55"]
|===
|Property |Default |Effect

|`micronaut.runner.mode`
|`run`
|`run` starts the application. `inspect` prints the index header, the build-time transforms (see
<<classTransforms,Class transforms>>) and the jar table, `list` prints the entries, and `extract` writes
an exploded copy. The non-`run` modes consume the remaining command line arguments.

|`micronaut.runner.timing`
|`false`
|Prints the time reached by each startup phase to standard error: archive opened, index read, class loader
ready, application entered. An archive that <<preload,preloads its startup classes>> also prints
`preload finished (N classes, M JDK classes)` when its background thread is done. Use it to separate launcher
cost from framework cost.

|`micronaut.runner.preload`
|`true`
|Set to `false` so that the launcher does not start the thread that
<<preload,preloads the recorded startup classes>>. It only has an effect on an archive packaged with a startup
profile or `startupClasses`.

|`micronaut.runner.mmap`
|from the archive (`archiveReads`)
|How the launcher reads the archive. `full` (or `true`) maps the whole file and defines `STORED` classes straight
from the mapping. `index` maps only the index and reads each class with one positional read into a pooled direct
buffer, so the class bytes stay in the page cache instead of the process's resident set: lower RSS, slightly
slower start (see <<archiveReads>>). `false` maps nothing and reads everything onto the heap; it is slower and
only needed on a platform or file system where mapping is unavailable or undesirable. Unset, or any other value,
follows the `archiveReads` option the archive was packaged with: `index` for `POSITIONAL`, and `full` for
`MAPPED`, the default. Thread interrupts are harmless in the `index` and `false` modes: a read that an interrupt
cuts short reopens the archive by its path and carries on. If that path no longer names the file this JVM
opened, class loading fails and asks for a restart, so publish new versions under new paths as described in the
archive lifetime section below.

|`micronaut.runner.verify`
|`false`
|Set to `true` to verify every entry's CRC-32 as it is read. Read once, when the launcher opens the archive.

|`micronaut.runner.parent`
|`platform`
|The parent of the application class loader. `platform` isolates the application from anything on the real

|`micronaut.runner.logback.precompiled`
|`true`
|`false` hands a precompiled Logback configuration (<<precompiledLogback>>) over to Logback's Joran at startup. It
has no effect on an archive without one.

|`micronaut.runner.static-services`
|`true`
|Set to `false` to ignore the static service table the archive was packaged with: Micronaut then scans for its

|`micronaut.runner.static-services.verify`
|`false`
|Set to `true` to compare the table with Micronaut's own scan on the first service lookup. A match prints

|`micronaut.runner.static-services.trace`
|`false`
|Set to `true` to print every lookup the table is asked for to standard error, as
`get <type> -> <count>`, `empty` or `dynamic`.

[[staticServices]]
== Static service table

When Micronaut starts, it finds its services (bean definitions, bean introspections, property source loaders,
type converters and so on) by scanning `META-INF/micronaut/` and `META-INF/services/` on the class path. A runner
JAR is packaged from a closed class path, so the packager records, for each service type, the implementation
names in the order that scan finds them, in classes it adds to the application under
`io.micronaut.runner.generated.services`. Micronaut reads this table through its `StaticOptimizations` hook instead
of scanning. Only discovery is precomputed: the table's classes instantiate each implementation the way Micronaut
instantiates it after a scan, and bean definitions are still loaded on the fork-join common pool.

The table is generated by default for micronaut-core `[5.1.10, 5.2)`. For another version, or whenever the
packager cannot prove the table equal to the scan, it generates none, or leaves a single service type to the scan,
and says why in the build log. micronaut-core 5.2 made the scan itself much cheaper, and the table did not show a
measurable gain on it. The `staticServices` packaging option turns it off. The table is an interim: once
micronaut-core ships a service index of its own
(https://github.com/micronaut-projects/micronaut-core/issues/13389[micronaut-projects/micronaut-core#13389]),
Runner will emit that instead.

What a table changes at run time:

* It describes the class path the application was packaged with. A lookup that names another class loader gets the
same answer, and a provider added after packaging is not seen: a JAR that an agent appends to the class path of an
extracted application, or a JAR replaced under `lib/`. Start with `-Dmicronaut.runner.static-services=false` in
those cases. With `-Dmicronaut.runner.parent=system` the table stands down by itself.
* `ClassLoader.getResources` and `java.util.ServiceLoader` are unchanged: they see one `META-INF/services/` file
per JAR.
* Implementations of the smaller service types are created on the thread that looks them up, not on a pool worker.
A provider that fails in a parallel load is reported with Micronaut's message, in a plain `RuntimeException`.
* A name condition given to `SoftServiceLoader.load(type, loader, condition)` is applied only by a micronaut-core
that passes it on to the table
(https://github.com/micronaut-projects/micronaut-core/issues/13388[micronaut-projects/micronaut-core#13388]).
* The thread that first uses `SoftServiceLoader` must have the application's class loader as its context class
loader, as the main thread does. Otherwise Micronaut does not find the table, and scans.
* An extracted application keeps the table, and so registers its beans in the order its runner JAR does.

[[archiveReads]]
== Mapped or positional reads

By default the launcher maps the whole runner JAR and defines each `STORED` class straight from the mapping. Every
page a class read touches then stays mapped in the process as a clean, file-backed page: it counts in the RSS that
`ps` and `top` report until the process exits, although the kernel can drop it at any time and it is not private
memory. Packaging with `archiveReads` set to `POSITIONAL`, or starting with `-Dmicronaut.runner.mmap=index`, maps
only the index instead and reads each class with one positional read into a direct buffer borrowed from a pool of
at most 16 buffers of at most 64 KiB; a larger class is read into a heap array.

Measured on `test-suite/samples/benchmark-large`, with paired, interleaved launches (30 pairs per run, two runs per
platform), positional reads against the default:

[cols="22,26,26,26",options="header"]
|===
|Platform |RSS at readiness |Private memory |Readiness

|macOS 26.6, Apple Silicon, Homebrew JDK 25.0.4.1
|-24 MiB; -20 to -23 MiB with the JDK AOT cache
|-3.0 to +0.8 MiB (`phys_footprint`)
|+9 to +11 ms (+2.1 to +2.4%); +8 ms (+3.1 to +3.2%) with the AOT cache

|Linux container, Temurin JDK 25.0.4+7, 6 CPUs
|-24 to -25 MiB without a cache
|+4 to +6 MiB without a cache (`RssAnon`)
|+13 ms (+3.2%); +7 to +9 ms (+3.0 to +3.9%) with the AOT cache
|===

The Runner JAR's resident mapping falls from 25 MiB (macOS) or 30 MiB (Linux) to 1.2 MiB, the index. Positional
reads change RSS, not page-cache use: in a Linux container the working set that Kubernetes reports
(`memory.current` minus `inactive_file`) did not drop, because the archive's pages sit on the inactive file list
whether they are mapped or read. The slower start is why `MAPPED` is the default.

[[preload]]
== Preloading the startup classes

Without a JDK cache, the launcher defines each class when something first asks for it, and most of those requests
come from the main thread while the framework starts. A runner JAR can instead carry the list of classes that a run
of the application loaded. The launcher then loads them, in that order, on one background thread while the
application starts, so that the main thread usually finds a class already defined.

Preloading is the accelerator for launches without a JDK cache. On `benchmark-large` (Micronaut 5.1.15, Netty
4.2.18) the uncached single JAR reached readiness about 100 ms sooner with its recorded list: -108.0 ms (95% CI -120.1
to -97.4, 60 pairs) on macOS with 12 CPUs and JDK 25.0.4.1, and -106.0 ms (95% CI -116.8 to -94.3, 20 pairs) in a Linux
container limited to 2 CPUs with JDK 25.0.4. The same class loading happens earlier and on two threads, which can cost
memory while the application starts: on macOS, private memory at readiness was 3 to 17 MiB higher from one session to
the next, with the process's peak footprint within 5 MB; in the container it rose by at most 2 MiB.

With a JDK AOT cache the recorded classes are already cheap to load, and preloading is not what makes a cached launch
fast: the same two runs measured -10.1 ms (95% CI -16.1 to -3.9) and -14.8 ms (95% CI -22.5 to +7.0). That small gain
has a memory cost of its own. With a cache the preloader gets through the whole list before readiness, and the list,
recorded without a cache over a whole run, names classes that a cached launch loads later or not at all: about 460
more classes were loaded at readiness. On macOS that was 5.4 MiB more private memory at readiness (95% CI 4.7 to 6.5
MiB, 60 pairs; 4 to 6.5 MiB across sessions), while in the container private memory did not change. To combine the
two, build the JAR with the list first and train the cache on that JAR (<<cdsAndAot>>).

*Record the profile.* The build records the list from the runner JAR it produces:

[source,bash]
----
./gradlew recordStartupProfile
mvn package mn-runner:record-startup-profile
----

It writes `src/main/micronaut-runner/startup-classes.txt`, the startup profile: the classes the runner class loader
defined up to the end of the workload, in load order, then as `jrt:` lines the JDK classes the run loaded from the
runtime image rather than from the JDK's default CDS archive, which the launcher loads after them. Commit it. From
then on `micronautRunnerJar` and `mn-runner:package` embed it with no configuration, and
`java -Dmicronaut.runner.mode=inspect -jar my-app-0.1-all.jar` prints `Preload classes N`, where N is the file's
`classes:` line. Recording launches the application, so it is never part of `assemble`, `build`, `check` or
`package`: it runs only when you ask for it.

The recording launch runs the production JAR with the JDK of the project's toolchain (Gradle) or of the
`maven-toolchains-plugin` (Maven), or else the one that runs the build. It passes a free port in
`MICRONAUT_SERVER_PORT` and removes `JAVA_TOOL_OPTIONS`, `JDK_JAVA_OPTIONS`, `_JAVA_OPTIONS` and `JDK_AOT_VM_OPTIONS`
from the environment, so no class cache takes part. Preloading is off, so an older profile is not replayed into the
new one, and `-Djava.util.concurrent.ForkJoinPool.common.parallelism=0` makes two recordings list the classes in nearly
the same order. The launch waits until the port accepts a connection, and then for the readiness path if one is set,
sends the workload, and reads the class-load log before it stops the application, so classes that only the shutdown
loads stay out. Every process it started is ended when the recording succeeds, fails, times out or is cancelled,
and when the build's JVM exits or is stopped in an orderly way, such as by SIGTERM on Linux and macOS. That last
cleanup runs in a shutdown hook, so a build JVM that is killed outright takes nothing down with it: after SIGKILL,
or when Windows terminates the process (as `taskkill /F` does), end the application yourself.

[[trainingSettings]]
*Training settings.* The workload decides a few hundred of the classes, so point it at the application's hot paths.
Without one, the launch sends a single `GET /` and the build warns.

[source,groovy]
----
micronaut {            // micronautRunner { } in a build without a Micronaut plugin
    runner {
        training {
            readinessPath = '/health'
            workloadPaths = ['/hello', '/orders']
        }
    }
}
----

In Maven each setting is the property `micronaut.runner.training.<name>`, with `-D` or in `<properties>`: lists are
comma-separated, timeouts are in seconds, and `environment` takes `NAME=value` entries.

[cols="22,18,60",options="header"]
|===
|Setting |Default |Meaning

|`readinessPath` |none |Once the port accepts a connection, `GET` it until it answers 2xx.
|`workloadPaths` |none |`GET` each path in order; each must answer 2xx.
|`workloadRepeat` |1 |How many times the paths are requested.
|`workloadCommand` |none |A command run after the paths, with `MICRONAUT_RUNNER_TRAINING_URL=http://127.0.0.1:<port>`.
It must exit 0.
|`runToExit` |`false` |For an application that exits by itself, such as one that is not a server: no readiness, workload
or stop, and it must exit 0. Then the list also holds what the shutdown loads.
|`stopPath` |none |`POST` it instead of ending the process, for example Micronaut's `/stop` endpoint with
`ENDPOINTS_STOP_ENABLED=true` and `ENDPOINTS_STOP_SENSITIVE=false` in `environment`.
|`jvmArgs` |none |JVM arguments of the recording launch. Name no class cache in them. The JDK AOT cache's launches
take `jdkAotCache.jvmArgs` instead (<<aotLayout>>).
|`environment` |none |Environment variables added to the launch.
|`portVariable` |`MICRONAUT_SERVER_PORT` |The variable that receives the port.
|`readinessTimeout`, `workloadTimeout`, `stopTimeout` |60 s, 60 s, 30 s |In Gradle a `java.time.Duration`.
|===

*Record it again* after upgrading Micronaut, Netty or any other dependency, or changing the JDK or the packaging
options, even when the build does not warn: a class that the application no longer loads stays listed and is loaded
for nothing. The build drops the names the archive no longer holds and says how many in one warning, and when more
than a tenth were dropped, that the profile looks stale.

*Another list.* An explicit `startupClasses` wins over the profile: the JVM's own class-load log, or a file with one
binary class name per line, where blank lines and lines starting with `#` are ignored and `jrt:<name>` marks a JDK
class. Set it on the extension (`micronaut { runner { startupClasses = file('startup-classes.log') } }`), on
`micronautRunnerJar`, or in Maven with `-Dmicronaut.runner.startupClasses=...` or `<startupClasses>`; by name, through
`options` or `<runnerOptions>`, the build fails. `null` falls back to the profile, so to build without it, delete the
file.

*When it does not run.* `-Dmicronaut.runner.preload=false` switches preloading off at run time. The launcher also
leaves the thread out when the JVM sees fewer than two processors, which in a container means a CPU limit of one:
there is no spare core for it to use. It applies only when the single JAR runs: the extracted layout (<<aotLayout>>)
has no launcher and ignores the list.

*A stale list is safe.* The list does not depend on the JAR's bytes. A class that is still in the archive but that
the application no longer uses is loaded for nothing: the launcher loads a listed class and never initialises it, so
nothing of the application runs early and its behaviour does not change, but the background work is wasted. A listed
JDK class that the runtime does not have, in a `jlink` image for example, is skipped.

*Agents.* An agent attached to the running JVM sees the preloaded classes as already loaded, so it has to
retransform them to instrument them. An agent started with `-javaagent` is unaffected: it transforms each class as
it is defined, on whichever thread defines it.

[[archiveLifetime]]
== Archive lifetime

As with any JAR a running JVM reads, a Shadow JAR included, do not modify, truncate or overwrite a runner
JAR while a JVM runs from it: publish each version under a new path. In the default `full` mode, STORED
classes are defined straight from the mapping, so truncating the file under a running JVM can terminate
the JVM instead of raising an exception; the JDK's own `ZipFile` does not memory-map the archive. The
recorded length (checked when the archive opens) and each nested JAR's local header (checked once, on
first use) are stale-archive diagnostics, not integrity protection or live-mutation detection.

== Running from an exploded layout

`extract` writes the archive out as a directory: the dependencies as real JAR files under `lib/`, and the
application classes in a JAR whose manifest names your main class and lists those dependencies in its
`Class-Path`.

[source,bash]
----
java -Dmicronaut.runner.mode=extract -jar my-app-0.1-all.jar --destination ./app
java -jar ./app/my-app-0.1-all.jar
----

The extracted form runs entirely on the JDK's own application class loader, with no custom class loader
anywhere. The single JAR also uses the JDK's ahead-of-time cache (<<cdsAndAot>>); what extraction adds is AOT
linking of the application classes, which classes defined by a user-defined class loader do not get. That is
why an application that will be started thousands of times in the same container image may be better served
by extracting once at image build time. For that cached deployment, trained and verified with its launch
options, see <<aotLayout>>.

=== Publication and replacement

Extraction writes the layout into a temporary sibling directory and renames it into place, so an interrupted
run leaves no partial tree. Without `--force`, a destination that exists and is not an empty directory,
including a symbolic link, is refused and left untouched, also when it appears while extraction runs. With
`--force`, the old destination (or only the link, when it is a symbolic link) is renamed to a sibling backup
until the new layout is in place; if publication fails it is restored, or the error names the backup.
