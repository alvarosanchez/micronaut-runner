====

Micronaut Runner packages a Micronaut application as one executable JAR that you run with `java -jar`. Compared with
a Shadow or Shade JAR, it starts noticeably faster without a JDK AOT cache, and uses less of the memory that a
process does not share with the OS page cache, at the cost of a slower, more thorough build
(<<performance,Performance>>). Unlike a shaded JAR, it keeps every dependency as a separate JAR inside it.

Gradle Shadow and Maven Shade flatten all dependencies into one namespace, which loses information:

* `META-INF/services` files from different dependencies collide and need merging.
* The Micronaut bean metadata under `META-INF/micronaut/` collides the same way.
* Signature files must be stripped, or the result fails verification.
* Each dependency's manifest, with its `Implementation-Version` and package sealing, is discarded.
* `META-INF/versions/` trees of several multi-release JARs are merged into one.

A Runner JAR keeps the boundaries, so duplicate resources, per-JAR manifests, sealed packages and multi-release JARs
behave as they do on an ordinary class path.

The Micronaut Gradle and Maven plugins build Runner JARs, and Micronaut Launch offers Runner as an alternative to
Shadow and Shade (<<quickStart,Quick Start>>).

.The shape of a Runner JAR
[source]
----
my-app-0.1-all.jar
├── META-INF/MANIFEST.MF          <1>
├── MICRONAUT-INF/index.bin       <2>
├── io/micronaut/runner/*.class   <3>
├── META-INF/micronaut/**         <4>
├── MICRONAUT-INF/classes/**      <5>
└── MICRONAUT-INF/lib/*.jar       <6>
----
<1> `Main-Class` points at the launcher
<2> an index of every entry, built when the archive is packaged
<3> the launcher, a few small classes that start your application
<4> the Micronaut bean metadata of every JAR, merged so that Micronaut reads it in one pass
<5> your application's own classes and resources
<6> the dependencies, each one a separate JAR

== How it starts faster

The index is built when the archive is packaged, so nothing is scanned at startup. The launcher maps the archive
into memory once and extracts nothing. By default, dependencies are stored uncompressed, so classes are defined
straight from the archive. Packaging also does once what a shaded JAR repeats at every start: it generates the
classes for lambdas, precomputes Micronaut's service lookups on micronaut-core 5.1, and compiles `logback.xml`
(<<whatChanges,What Changes for Your Application>>). The archive is larger on disk than a shaded JAR, but smaller
compressed.

Two features share the letters AOT. _Micronaut AOT_ generates optimized application code when you build
(<<micronautAot,Micronaut AOT>>). The _JDK AOT cache_ is a file the JVM writes during a training run of your
application, and reads at every later start (<<jdkAotCache,The JDK AOT Cache>>). Runner works with both.

== When Runner is not the right fit

* You build a GraalVM native image. Runner packages JVM applications only.
* You deploy a serverless function, such as on AWS Lambda, Google Cloud Functions, Azure Functions or Oracle
Functions. The function host loads your handler itself and never runs the archive's main class.
* Your build relies on Shadow relocation to rename packages. Runner never relocates.
* You deploy only the container image that `./gradlew dockerBuild` or `mvn package -Dpackaging=docker` builds. That
image is built in layers from your classes and dependency JARs, not from the Runner JAR, so Runner changes nothing in
it.

A few third-party libraries behave differently in a Runner JAR. <<compatibility,Compatibility and Limitations>> lists
them, with the workaround when there is one.

Start with <<quickStart,Quick Start>>, then read <<whatChanges,What Changes for Your Application>>.
