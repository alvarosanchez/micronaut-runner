These figures compare packagings of one Micronaut Netty service with about 50 dependencies, on JDK 25 and 27, on a
multi-core developer machine, timing fresh JVM starts from launch to the first HTTP response. Your results depend on
your dependencies, CPUs and JDK, and on the OS page cache. _RSS_ counts all of a process's memory, including pages of
files it maps; _private memory_ counts only what it does not share with the page cache.

* Without a JDK AOT cache, a Runner JAR built with the defaults reaches its first response in about 25–30% less time
than a Shadow JAR of the same application, with about a fifth less RSS and over a third less private memory.
* On disk, the default archive is about two and a half times the size of a shaded JAR. Gzipped, as image layers and
downloads travel, it is about a third smaller.
* A JDK AOT cache cuts startup time by about half for a Shadow JAR and by about 40% for a Runner JAR. With a cache on
both sides, they start in about the same time; which one is a few percent ahead depends on the JDK, the Micronaut
version and the machine. The single Runner JAR then uses up to about 10% less private memory, and more RSS, because
it maps the archive.
* With their caches, the extracted layout and the single JAR start in about the same time, and the layout has about
15% lower RSS. Without its cache, the layout takes 10–15% more time than the single JAR.
* A startup profile cuts a start without a cache by about a further fifth, for a few percent more private memory.
With a cache, it gains a few percent.
* Without a JDK cache, the plain Runner JAR takes about a fifth less time than Micronaut AOT's optimized Shadow JAR,
and the optimized Runner JAR about a quarter less. With a cache on both sides, they start in about the same time.

.Trade-offs of the options, compared with the defaults
[cols="1,3",options="header"]
|===
|Option |Trade-off

|`PRESERVE` |15–20% more start time and more memory; about the size of a shaded JAR, and about 50% larger gzipped
than the default. Still about 15% less time than Shadow.
|`HYBRID` |Starts like the default; about a quarter smaller on disk, about a third larger gzipped.
|`POSITIONAL` reads |About 15% lower RSS, a start one or two percent slower, the same private memory.
|`mmap=false` |A few percent slower, more private memory.
|Lambdas left to the JDK |About 10% more start time without a cache and 15% with one, about a quarter more private
memory, an archive about 10% smaller. No measurable effect on the extracted layout.
|Another default step off |A few percent more start time each. Keeping local-variable tables changes nothing with a
cache, and makes the archive about 15% larger.
|Bean definition prefetch |A few percent less time on machines with many cores, nothing measurable on small ones.
|Reflection instead of the entry stub |No measurable difference.
|Dynamic CDS instead of the AOT cache |10–15% more start time, a file about 40% smaller.
|===

Packaging does more work than shading: it rewrites classes, compiles `logback.xml` and precomputes service lookups,
once per build, so that every start does less. That is the intended trade.

To measure your own application, build both JARs (<<quickStartGradle>>), start each several times as a fresh JVM,
alternating between them, and time each start to its first response. `-Dmicronaut.runner.timing=true` tells launcher
time from framework time. The
https://github.com/{githubSlug}/blob/master/benchmarks/README.md[benchmark harness] describes the method in full.
