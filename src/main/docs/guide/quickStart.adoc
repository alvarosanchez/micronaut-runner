== Prerequisites

Micronaut Runner needs Java 25 in two places: the JVM that runs Gradle or Maven, and the JVM that runs the
packaged application. A compilation toolchain does not change the build-tool JVM, so check
`./gradlew --version` or `mvn -version` as well as `java -version`.

== Gradle

Apply the plugin alongside the Micronaut application plugin:

[source,groovy]
----
plugins {
    id 'io.micronaut.application' version '5.0.2'
    id 'io.micronaut.runner.standalone' version '{version}'
}
----

NOTE: `io.micronaut.runner.standalone` is an interim plugin. The `io.micronaut.runner` plugin of micronaut-gradle-plugin
(https://github.com/micronaut-projects/micronaut-gradle-plugin/issues/1378[micronaut-projects/micronaut-gradle-plugin#1378])
will replace it, with the same task names and the same `micronaut { runner { } }` block, so moving to it is a change of
plugin ID. Applying both fails the build with `The io.micronaut.runner plugin from micronaut-gradle-plugin builds the
Runner JAR in this build. Remove io.micronaut.runner.standalone: ...`. Only when a Micronaut plugin, this plugin and then
`io.micronaut.runner` are applied in that order does the build fail earlier, with Gradle's `Cannot add extension with
name 'runner', as there is an extension already registered with that name.`

That is the whole configuration. The plugin adds a `micronautRunnerJar` task, wires it into `assemble`,
and takes your main class from the `application` block and your dependencies from the runtime classpath,
in resolution order.

[source,bash]
----
./gradlew micronautRunnerJar
java -jar build/libs/my-app-0.1-all.jar
----

The archive is named with the `all` classifier, the same name the Shadow plugin uses, so existing
Dockerfiles and CI scripts that reference `build/libs/*-all.jar` keep working.

WARNING: Do not apply the Shadow plugin and configure it to write the same file. The two produce different
archives under one name. The plugin fails the build if it detects that.

=== Configuration

In a build that applies a Micronaut plugin, the packaging options go in `micronaut { runner { } }`:

[source,groovy]
----
micronaut {
    runner {
        // false skips every task the plugin registers.
        enabled = true

        // STORED re-packs dependencies uncompressed so classes are defined straight from the mapped file.
        // PRESERVE copies each dependency byte for byte: smaller on disk only (its gzip size is about 1.4x
        // STORED's), and it loads more slowly.
        compression = 'STORED'

        // Enter main through a generated direct call instead of reflection.
        entryStub = true

        // Set this only when the application's own output is a multi-release JAR.
        multiRelease = false

        // Written into the manifest, so users need not pass the matching command line flags.
        addOpens.add('java.base/java.lang')
        addExports.add('java.base/sun.nio.ch')
        enableNativeAccess = true

        manifestAttributes.put('Implementation-Vendor', 'Example Ltd')

        // Options without a typed property, by name (see the table below):
        // options.put('<name>', '<value>')
        // options.put('precompileLogback', 'false') // On by default: compiles logback.xml at packaging time; anything it cannot compile is left to Logback.
    }
}
----

`micronautRunner { }` is the same extension under another name, for a build without a Micronaut plugin. Each option is
also a property of the `micronautRunnerJar` task, which takes the extension's value as its default: a setting on the
task wins for that task.

Micronaut Runner's packaging library owns every option, its default and its validation; the plugins only pass
what you set. Every option can be set by name, with the value as text: `true` or `false` for a boolean, a
comma-separated list, or one `Name: value` line per manifest attribute. An option set by name wins over its
typed property, and an unknown name fails the build.

[cols="2,1,1,1,1",options="header"]
|===
|Option |Type |Default |Exposure |Since

|`compression` |`STORED` or `PRESERVE` |`STORED` |typed |1.0
|`entryStub` |boolean |`true` |typed |1.0
|`multiRelease` |boolean |`false` |typed |1.0
|`enableNativeAccess` |boolean |`false` |typed |1.0
|`addOpens` |list |empty |typed |1.0
|`addExports` |list |empty |typed |1.0
|`manifestAttributes` |map |empty |typed |1.0
|`precompileLogback` |boolean |`true` |passthrough |1.0
|===

A typed option has a property of its own, in Gradle and in Maven. A passthrough option is set only by name,
through `options` in Gradle and `<runnerOptions>` or `-Dmicronaut.runner.<name>` in Maven, and needs no plugin
release.

The entry stub is generated only when the main class is a public, non-abstract class in a named package that
declares its own `public static void main(String[])`, in every selectable version of a multi-release application.
Otherwise the packager reports why and the launcher calls `main` through reflection.

`addOpens` and `addExports` entries are `module/package` pairs in manifest syntax, with no `=ALL-UNNAMED` suffix,
and invalid entries fail packaging.

`precompileLogback` compiles `logback.xml` into a Logback `Configurator` when it is packaged, and leaves any file it
cannot reproduce exactly to Logback; see <<precompiledLogback>>.

The application's `+Implementation-*+`, `+Specification-*+` and `Sealed` attributes and package sections come from the
`jar` task's manifest configuration, including `manifest.from(...)` merges; `micronautRunnerJar` does not build the
thin JAR. If the `jar` task adds attributes in `doFirst` or `doLast`, or merges a file that another task generates,
set `applicationJar = tasks.named('jar').flatMap { it.archiveFile }`.

`manifestAttributes` may override attributes imported from the application's manifest, but `Manifest-Version`,
`Main-Class` and `Micronaut-Runner-*` attributes are reserved and rejected.

Dependencies that are JAR files are nested, a dependency that is a directory fails the build, and any other
file, such as a POM, is skipped with a warning.

The main class and the archive's name are properties of the task only:

[source,groovy]
----
micronautRunnerJar {
    // Defaults to application.mainClass
    mainClass = 'com.example.Application'

    // Defaults to all
    archiveClassifier = 'executable'
}
----

The task names the archive `<archiveBaseName>-<archiveVersion>-<archiveClassifier>.jar` and writes it to
`destinationDirectory`. These default to `base.archivesName`, the project version, `all` and `base.libsDirectory`, so
`base { libsDirectory = ... }` moves the archive with every other JAR of the project. In a build that applies
`io.micronaut.application`, do not choose `runner` as the classifier: the Docker plugin's `runnerJar` task already
writes `-runner.jar`.

=== Publishing

The plugin exposes the archive as the `micronautRunnerElements` configuration. Its `Usage` attribute is
`micronaut-runner`, so a Java consumer of the project never selects it by accident; another project of the build
takes it by name, with `project(path: ':app', configuration: 'micronautRunnerElements')`.

To publish the archive with `maven-publish`, add it to the publication:

[source,groovy]
----
publishing {
    publications {
        maven(MavenPublication) {
            from components.java
            artifact(tasks.named('micronautRunnerJar').flatMap { it.archiveFile }) {
                classifier = 'all'
                builtBy tasks.named('micronautRunnerJar')
            }
        }
    }
}
----

== Maven

NOTE: This Maven plugin is interim. The `runner` packaging of micronaut-maven-plugin
(https://github.com/micronaut-projects/micronaut-maven-plugin/issues/1720[micronaut-projects/micronaut-maven-plugin#1720])
will replace it, and this plugin's `package` goal fails in a project with `runner` packaging, even when it is skipped.

Add the plugin to your build. Bind it to `package`, so it runs after the JAR is built:

[source,xml]
----
<plugin>
    <groupId>io.micronaut.runner</groupId>
    <artifactId>micronaut-runner-maven-plugin</artifactId>
    <version>{version}</version>
    <executions>
        <execution>
            <goals>
                <goal>package</goal>
            </goals>
        </execution>
    </executions>
</plugin>
----

[source,bash]
----
mvn package
java -jar target/my-app-0.1.jar
----

By default the runner JAR replaces the project's main artifact, exactly as the Shade plugin does, and the
JAR produced by `maven-jar-plugin` is kept alongside it as `original-my-app-0.1.jar`. Set a `classifier` to
attach it as an additional artifact instead and leave the main one untouched.

The main class is taken from the `exec.mainClass` property, which the Micronaut parent POM already sets.

In Maven, each `addExports`/`addOpens` entry is its own element:

[source,xml]
----
<configuration>
    <addExports>
        <addExport>java.base/sun.nio.ch</addExport>
    </addExports>
    <addOpens>
        <addOpen>java.base/java.lang</addOpen>
    </addOpens>
</configuration>
----

The typed options are parameters of the same names, except that `manifestAttributes` is `<manifestEntries>`; the
scalar ones also read `-Dmicronaut.runner.<name>`. `<runnerOptions>` and `-Dmicronaut.runner.<name>` set the same
options by name, `-Dmicronaut.runner.<name>` only for passthrough options, and a `<runnerOptions>` entry wins. For
example, `-Dmicronaut.runner.precompileLogback=false` leaves `logback.xml` to Logback at startup.

== What to check first

[source,bash]
----
java -Dmicronaut.runner.mode=inspect -jar my-app-0.1-all.jar
----

prints the format version, the number of dependencies and entries, and the application main class, which
confirms the archive is what you expect before you deploy it.
