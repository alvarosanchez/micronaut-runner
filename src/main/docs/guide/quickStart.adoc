== Prerequisites

Micronaut Runner's published libraries and build plugins target Java 25. Use a JDK 25 installation to run
the build and Java 25 to launch the packaged application. JDK 25 is the supported baseline. The project's
non-blocking early-access JDK 26 CI job is a forward-compatibility signal, not a requirement or an unlimited
compatibility guarantee for later JDKs.

The Java installations selected for the shell, the build tool, application compilation and deployment can
be different. In particular, a Gradle or Maven Java toolchain controls application compilation; it does not
change the build-tool JVM that loads the Micronaut Runner plugin. Point `JAVA_HOME` at JDK 25 (and put its
`bin` directory first on `PATH`) before invoking Gradle or Maven. If the build has an explicit Gradle daemon
JVM or Maven launcher configuration, update that selection as well. The deployment image or host that runs
the resulting runner JAR must also provide Java 25; selecting a Java 25 compilation toolchain alone does not
update that runtime.

Check each relevant JVM before applying the plugin or launching the application:

[source,bash]
----
java -version
./gradlew --version
mvn -version
----

`java -version` reports the shell and deployment command's runtime. In `./gradlew --version`, verify the
launcher and daemon JVM; in `mvn -version`, verify the reported Java version and runtime path. Each must show
the intended JDK 25 installation for the corresponding quick-start path.

== Gradle

Apply the plugin alongside the Micronaut application plugin:

[source,groovy]
----
plugins {
    id 'io.micronaut.application' version '5.0.2'
    id 'io.micronaut.runner' version '{version}'
}
----

That is the whole configuration. The plugin adds a `micronautRunnerJar` task, wires it into `assemble`,
and takes your main class from the `application` block and your dependencies from the runtime classpath,
in resolution order.

[source,bash]
----
./gradlew micronautRunnerJar
java -jar build/libs/my-app-0.1-all.jar
----

The archive is named with the `all` classifier, the same name the Shadow plugin uses, so existing
Dockerfiles and CI scripts that reference `build/libs/*-all.jar` keep working.

WARNING: Do not apply the Shadow plugin and configure it to write the same file. The two produce different
archives under one name. The plugin fails the build if it detects that.

=== Configuration

Every setting is a property of the task:

[source,groovy]
----
micronautRunnerJar {
    // Defaults to application.mainClass
    mainClass = 'com.example.Application'

    // STORED re-packs dependencies uncompressed so classes are defined straight from the mapped file.
    // PRESERVE copies each dependency byte for byte, producing a smaller archive that loads more slowly.
    compression = 'STORED'

    // Both build plugins default to requesting an entry stub. The low-level RunnerJarSpec builder does not.
    entryStub = true

    // Set this only when the application's own output is a multi-release JAR.
    multiRelease = false

    // Written into the manifest, so users need not pass the matching command line flags.
    addOpens.add('java.base/java.lang')
    addExports.add('java.base/sun.nio.ch')
    enableNativeAccess = true

    manifestAttributes.put('Implementation-Vendor', 'Example Ltd')
}
----

The application's `Implementation-*`, `Specification-*` and `Sealed` attributes and package sections come from the
`jar` task's manifest configuration, including `manifest.from(...)` merges; `micronautRunnerJar` does not build the
thin JAR. If the `jar` task adds attributes in `doFirst` or `doLast`, or merges a file that another task generates,
set `applicationJar = tasks.named('jar').flatMap { it.archiveFile }`.

`manifestAttributes` may override attributes imported from the application's manifest. `Manifest-Version`,
`Main-Class` and every attribute whose name begins with `Micronaut-Runner-` are reserved for the runner
format and are rejected case-insensitively.

The low-level `RunnerJarSpec.Builder.manifestAttributes` API preserves the map's iteration order. Pass a
deterministically ordered map, such as `LinkedHashMap`, when builds in separate JVMs must produce identical
bytes. Code that wants logical map equality to be the reproducibility input can instead call
`canonicalManifestAttributes`; it sorts names lexicographically without using the default locale and rejects
two names that differ only by case, because manifest attribute names are case insensitive.

`addExports` and `addOpens` use executable-JAR manifest syntax in both plugins and in
`RunnerJarSpec.Builder`: each list entry is exactly one `module/package` pair. The packager joins multiple
entries with spaces in `Add-Exports` or `Add-Opens`. Do not append `=ALL-UNNAMED`; that target is implicit in
the manifest. The suffix belongs only to the equivalent Java command-line options, for example
`--add-exports java.base/sun.nio.ch=ALL-UNNAMED`. Invalid entries fail packaging rather than being written
into a manifest the JDK would ignore.

== Maven

Add the plugin to your build. Bind it to `package`, so it runs after the JAR is built:

[source,xml]
----
<plugin>
    <groupId>io.micronaut.runner</groupId>
    <artifactId>micronaut-runner-maven-plugin</artifactId>
    <version>{version}</version>
    <executions>
        <execution>
            <goals>
                <goal>package</goal>
            </goals>
        </execution>
    </executions>
</plugin>
----

[source,bash]
----
mvn package
java -jar target/my-app-0.1.jar
----

By default the runner JAR replaces the project's main artifact, exactly as the Shade plugin does, and the
JAR produced by `maven-jar-plugin` is kept alongside it as `original-my-app-0.1.jar`. Set a `classifier` to
attach it as an additional artifact instead and leave the main one untouched.

The main class is taken from the `exec.mainClass` property, which the Micronaut parent POM already sets.

Both plugins request a generated entry stub by default; the low-level `RunnerJarSpec.Builder` default is
`false`. A request produces a stub only when the main class is a public, non-abstract class in a named
package that declares its own `public static void main(String[])`. For a declared multi-release application,
every selectable version of the main class must have that shape. Otherwise the packager reports the reason,
records no stub in the index and the launcher enters the application through its reflective fallback. The
request is therefore not a promise that a stub will be present or that startup will be faster.

The Maven list syntax follows the same manifest grammar:

[source,xml]
----
<configuration>
    <addExports>
        <addExport>java.base/sun.nio.ch</addExport>
    </addExports>
    <addOpens>
        <addOpen>java.base/java.lang</addOpen>
    </addOpens>
</configuration>
----

== What to check first

[source,bash]
----
java -Dmicronaut.runner.mode=inspect -jar my-app-0.1-all.jar
----

prints the format version, the number of dependencies and entries, and the application main class, which
confirms the archive is what you expect before you deploy it.
