This chapter documents the archive layout. You do not need any of it to use Micronaut Runner; it is here so
the format can be inspected, reimplemented and reasoned about.

== Outer archive

Every entry of the outer archive is `STORED`, that is, uncompressed. That is what allows a nested JAR's
bytes to be read in place at a known offset.

[cols="35,65"]
|===
|Entry |Purpose

|`META-INF/MANIFEST.MF`
|Written first. `Main-Class` is `io.micronaut.runner.Launcher`. `Micronaut-Runner-Format` carries the
format version, `Micronaut-Runner-Start-Class` the application main class, for information only.

|`MICRONAUT-INF/index.bin`
|Written second, so the launcher finds it after reading only a couple of central directory records.

|`+io/micronaut/runner/**.class+`
|The launcher. Only class files are copied from the launcher library; its manifest and Maven metadata are
not.

|`MICRONAUT-INF/transforms.txt`
|Present only when a build-time transform changed a class or recorded a fallback: tab-separated lines, the first
naming the Runner version, then one per nested JAR and transform with its counts, then one `lambdas` line per
JAR, or for the application layer, with the lambda call sites rewritten and left. It is not indexed, the launcher
never reads it at run time, and `extract` ignores it; `inspect` prints it. See
<<classTransforms,Class transforms>>.

|`+META-INF/micronaut/**+`
|The Micronaut bean metadata of the application and of every dependency, merged and de-duplicated, with
explicit directory entries. See <<serviceDiscovery>>.

|`MICRONAUT-INF/classes/`
|An explicit directory entry for the application layer, so that the `CodeSource` location of every
application class names something the archive really carries and can be opened.

|`+MICRONAUT-INF/classes/**+`
|The application's own classes and resources, stored exploded. This is "jar 0"; an entry's _logical name_
is its path with this prefix removed. Directories inside the layer are not stored; the index carries a
synthetic record for each one instead.

|`MICRONAUT-INF/lib/<name>.jar`
|The dependencies, in classpath order, each a complete JAR.
|===

By default each dependency is re-packed so that its own entries are `STORED` too, which removes
decompression from class loading at the cost of a larger archive. Re-packing also drops signature files
(`+META-INF/*.SF+`, `+*.DSA+`, `+*.RSA+`, `+*.EC+`, `+META-INF/SIG-*+`) and `META-INF/INDEX.LIST`. Manifests are
never rewritten, so package metadata and sealing survive intact. By default, re-packing also strips
local-variable tables from dependency classes, which then carry new CRC-32 values; see
<<localVariableTables,Local-variable tables>>. By default it also rewrites eligible lambda call sites and adds a
generated `$$Lambda$R<n>` class after each host, so those entries get new CRC-32 values too, and the application
layer's lambdas are rewritten the same way; see <<desugaredLambdas,Desugared lambdas>>. The `PRESERVE` option
copies each dependency byte for byte instead.

With a startup class list (`startupClasses`, which the recorded startup profile provides), re-packing also writes
each nested JAR's startup classes first, in the order they were recorded, after `META-INF/` and the manifest. The
bytes startup reads are then contiguous instead of scattered through every dependency. Nested JARs keep their
places in the outer archive and class path order, so lookups and duplicate precedence do not change.

The `HYBRID` option re-packs as `STORED` does, startup classes first, but keeps the other classes compressed. An
unlisted class that no build-time transform changed keeps its original compressed bytes, and one a transform
rewrote or generated is deflated afresh. Listed classes, resources, and the few classes the dependency stored or
that do not get smaller stay stored.

// HYBRID_TABLE: filled in from the measured runs of the pull request that adds HYBRID.

Use `HYBRID` only where on-disk or unpacked size matters more than transfer size: DEFLATE bytes do not compress
again, so a `HYBRID` image layer is larger after gzip than a `STORED` one. It needs the startup profile (see
<<preload,Preloading the startup classes>>). Without one, it writes the nested JARs `STORED`, with a warning, so
the first build of a project, before it has recorded a profile, still succeeds. An unlisted class costs about 3 µs
of inflation when it is loaded, so record the profile again after a dependency upgrade. Because the rewritten cold
classes are deflated afresh, a `HYBRID` archive's bytes depend on the build JDK and the zlib it uses.

Shadow can also write `STORED` entries (`entryCompression = ZipEntryCompression.STORED`), so the gain from not
inflating is not specific to this format; <<benchmarks,Benchmarks>> measures the two effects separately.

== The index

`MICRONAUT-INF/index.bin` is a little-endian binary structure designed to be used directly from the memory
mapping, with bounds checks but no parsing into objects. It consists of a fixed 128-byte header followed
by five sections: a jar table, a package table, an entry table, a hash table and a string table. An archive
packaged with a startup class list has up to two more after them: a preload table and a JDK preload table. The exact
byte layout is defined, as compile-time constants with documentation, in `IndexFormat` in the
`micronaut-runner-launcher` artifact, which is the authoritative description. An archive packaged with
`archiveReads` set to `POSITIONAL` carries a header flag that makes the launcher map only the index and read classes
with positional reads, and its header records the largest `STORED` class, which sizes the launcher's read buffers.

The parts worth understanding:

Entry records:: One per entry, per jar, carrying the entry's absolute offset in the outer file, its sizes,
CRC-32, compression method and MS-DOS timestamp. Records for one jar are contiguous, with the physical
entries first in the nested JAR's central directory order, which puts the startup classes first when a startup
class list is given, so `JarFile.entries()` can report them faithfully.

Hash table:: Maps a logical name to the first record with that name, using open addressing and linear
probing. The maximum probe length actually needed is recorded at build time and validated when the index
is opened, so a lookup has a hard bound.

Same-name chains:: Entries that share a logical name are linked in classpath order, so `getResource`
returns the first and `getResources` walks the chain, emitting one URL per contributing JAR.

Multi-release aliases:: For a JAR declaring `Multi-Release: true`, each `META-INF/versions/N/<path>` entry
is indexed a second time under `<path>`, marked with its version. Aliases precede the base entry in
descending version order, so resolution takes the first record the running JDK accepts. The rule for what
counts as a version directory is `java.util.jar.JarFile`'s, so that a JAR resolves to the same bytes
inside a runner JAR as it does on an ordinary class path: `N` must start with `1`-`9`, so
`META-INF/versions/09/` is an ordinary entry and is never selected; `N` is considered from 8 upwards, and
only when the effective runtime version is above 8, so a versioned entry is ignored altogether when
`jdk.util.jar.enableMultiRelease` is `false` or `jdk.util.jar.version` selects 8; and paths that themselves
start with `META-INF/` are never aliased.

Package table:: The per-package `Name:` sections of each dependency's manifest, which override the
manifest's main attributes attribute by attribute when a package is defined.

Preload tables:: Optional, and written only for an archive packaged with `startupClasses`
(<<preload,Preloading the startup classes>>). The
preload table is a `u32` array of entry record indexes, one per recorded class of the archive, in the order the
classes were first loaded; each is the record a class lookup by that name finds first, which for a multi-release
class is the head of the chain that holds its versioned aliases. Header bytes 96-103 hold its offset and bytes
104-107 its length. The JDK preload table is a `u32` array of string references to the binary names of the recorded
JDK classes, which no JDK is consulted about; bytes 108-111 hold its length and bytes 112-119 its offset. Each
table starts at the next 8-byte boundary after what precedes it: the string table, then the preload table.
Without a list all 24 bytes are zero and the index ends with the string table, byte for byte what it was before
these tables existed, so the format version is unchanged.

=== Detecting a stale archive

The index stores the outer file's length, and every jar record stores the offset of the local file header
that introduces it. The length is checked when the archive opens and each header once, on the JAR's first
use; a mismatch fails with a message telling you to rebuild. This detects an archive that was appended
to, truncated or re-zipped after packaging, which would otherwise mean reading from wrong offsets. It is
a staleness check, not an integrity check: a modification that preserves the length and the header
positions passes it. Full CRC verification on every read is available with
`-Dmicronaut.runner.verify=true`. See <<archiveLifetime,archive lifetime>>.

[[serviceDiscovery]]
== Micronaut service discovery

Micronaut locates beans by calling `getResources("META-INF/micronaut/")` and then _listing the directory_
that each returned URL denotes. Listing a directory is not something a URL can do generically, so the
framework opens the archive behind the URL. For a JAR nested inside another JAR it has to mount a ZIP file
system over a ZIP file system, and the JDK implements that by reading the whole inner archive into memory.
Doing this once per dependency would dominate startup.

Micronaut Runner avoids it by merging that metadata at build time. Every
`META-INF/micronaut/<service>/<name>` entry from the application and from every dependency is written,
de-duplicated and in classpath order, into `META-INF/micronaut/` at the *root* of the outer archive, with
real directory entries. The class loader resolves any name under that prefix against the merged copy
alone, so `getResources("META-INF/micronaut/")` returns exactly one URL and Micronaut lists it in a single
pass over an archive the JVM already has open.

Almost all of these entries are empty markers whose name carries the information, but one that has content
keeps it: the merged copy is written with the bytes of the first contributor in classpath order, and a
build warns when two JARs contribute the same name with different content. Since every lookup under the
prefix is answered from the merged copy, the alternative would be serving an empty stream for a file that
is not empty.

Classic `META-INF/services/` files are left exactly where they are, one per dependency: they are read as
files through their URL, which works per JAR without any special handling.

For an application whose micronaut-core the packager knows, it also adds a _static service table_ to the
application layer: a few classes under `io/micronaut/runner/generated/services/`, and the line in
`META-INF/services/io.micronaut.core.optim.StaticOptimizations$Loader` that registers them, put in front of the
application's own file when it has one. The table lists, for each service type, the names in every JAR's
`META-INF/services/` file and in the merged directory, in the order Micronaut's scan finds them, so that Micronaut
reads neither when the application starts. See <<staticServices,Static service table>>.
