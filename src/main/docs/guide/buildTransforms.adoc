Packaging can do work once, at build time, that an application would otherwise repeat at every start. Each
transformation is an option of the Runner JAR, fails closed, and names in the build log why it did nothing when it
does nothing.

There are two kinds. <<precompiledLogback>> adds generated classes to the application layer, and
<<classTransforms>> rewrites the classes of the dependencies as they are re-packed, first of all by dropping their
<<localVariableTables,local-variable tables>>. Both are on by default, and neither touches what the other produces:
the class transforms never rewrite the application layer, where the generated Logback classes go, and the Logback
front end runs the application's Logback JARs as they were published, not their re-packed copies.

[[precompiledLogback]]
== Precompiled Logback configuration

Runner JARs precompile logback.xml by default; Shadow JARs, Docker images and native images configure Logback with
Joran at startup unless Micronaut AOT's `logback.xml.to.java` has replaced `logback.xml`, so switching a project from
Shadow to Runner changes how Logback is configured. The opt-out restores Joran.

Without it, Logback parses `logback.xml` on the main thread at every start: it loads the JDK's XML parser and
Joran's model classes, and `io.micronaut.runtime.Micronaut` waits for it. With it, the packager reads the file with
Logback's own parser, in an isolated class loader that holds only the application's Logback and SLF4J jars, and
generates `io.micronaut.runner.generated.logback.LogbackConfigurator`, registered as a
`ch.qos.logback.classic.spi.Configurator` service. At startup that class creates the appenders and sets the loggers
the file declares, in the order Joran does, without XML. `logback.xml` stays in the archive.

=== What is compiled

A file is compiled only when all of it is within this subset:

* `<configuration>` without `debug`, `scan`, `scanPeriod` or `packagingData`, or with them `false`;
* `<appender>` elements of public `ch.qos.logback` appender classes, such as `ConsoleAppender` and `FileAppender`,
with `String`, `boolean` or `int` properties (`<target>`, `<file>`, `<append>`) and at most one `<encoder>`, a
`PatternLayoutEncoder` whose only child is a `<pattern>` using Logback's built-in conversion words;
* `<logger>` (name, level, `additivity`) and `<root>` elements that contain only `<appender-ref>`s.

No value may use a variable. Anything else, such as `<property>`, `<include>`, `<if>`, `<conversionRule>`, a
`<filter>`, a `<rollingPolicy>` or a custom appender, leaves the file to Joran. So does a file Joran itself
corrects or complains about: two appenders writing to the same `<file>`, a property element without text, or a
`<name>` element inside an appender.

=== When nothing is compiled

The packager also leaves the file to Joran when logback-classic, logback-core or slf4j-api is missing, when the two
Logback jars differ in version or are outside 1.5.37 to 1.6 (exclusive), when there is no `logback.xml`, when any
layer has a `logback-test.xml`, `logback.groovy` or versioned Logback file, when any layer already registers a
`Configurator` (your own, or Micronaut AOT's), and when a packaged `application*` or `bootstrap*` file may set
`logger.config` or `logback.configurationFile`. That last check errs on the side of Joran: a `.properties` file is
parsed, and any other format counts when its text names `configurationFile` or `logger.config`, or has the word
`logger` and a `config` key anywhere, whatever the nesting or the line breaks. The build logs one line either way,
at info level: `Precompiled logback.xml (application layer) into ...` or `No Logback configuration was precompiled
because <reason>; Logback will configure itself with Joran at startup`. A generated class name that is already
taken is a warning.

=== At runtime

The generated configurator hands the configuration to Joran when:

* `-Dlogback.configurationFile` is set;
* Micronaut refreshes logging (any `logger.*` property does) and `-Dlogger.config`, `LOGGER_CONFIG`, or an
environment variable named `logger.config` or `logback.configurationFile`, names a location: that file is
configured, as without Micronaut Runner;
* `-Dlogback.debug` or `-Dlogback.statusListenerClass` asks for Logback's status output;
* `-Dmicronaut.runner.logback.precompiled=false` is set.

What changes when it applies: Joran's INFO status messages about reading `logback.xml` are not recorded, and every
way to see them falls back to Joran. `logback.xml` is read only on the paths above.

One case is not covered: a `logger.config` set by configuration outside the archive, such as
`-Dmicronaut.config.files`, an `application.yml` in the working directory or a `--logger.config` program argument,
is not applied once a `Configurator` is registered, and the runtime opt-out does not change that. Set the location
with `-Dlogger.config` or `LOGGER_CONFIG` instead, or turn precompilation off.

=== Turning it off

[source,groovy]
----
micronaut {
    runner {
        options.put('precompileLogback', 'false')
    }
}
----

In Maven, pass `-Dmicronaut.runner.precompileLogback=false`, or add `<precompileLogback>false</precompileLogback>` to
`<runnerOptions>`.

[[classTransforms]]
== Dependency class transforms

A runner JAR re-packs every dependency, and with the default `STORED` compression it can also rewrite the
dependency classes on the way: whatever a class carries that the application never needs at run time is paid for
again on every start. This section lists what Runner changes in dependency classes at build time, the default
and the opt-out of each change, and what an application can observe as a result.

Every change runs in one pass: each dependency class is parsed once, every enabled transform is applied to it, and
the result is written once. Before a rewritten class is accepted it is verified, with the JDK's class-file
verifier, against the whole runtime class path and the JDK's own classes; a transform that fails on a class, or
makes it verify worse than the class it replaces, is dropped for that class alone, and the build log says so.

Nothing here applies to the application's own classes, the ones Runner generates into the application layer
included, to a project dependency (another project of a Gradle build, another module of a Maven reactor), or to
any class of a signed JAR: they are nested exactly as they were built. With `PRESERVE` compression every
dependency is nested byte for byte, so none of these transforms run.

What a build changed is recorded in the archive, in `MICRONAUT-INF/transforms.txt` (see <<format>>), and printed
by the `inspect` mode:

[source,bash]
----
java -Dmicronaut.runner.mode=inspect -jar build/libs/my-app-0.1-all.jar
----

[[localVariableTables]]
=== Local-variable tables

On by default. A dependency class loses the tables that name its local variables, and its constant pool is rebuilt
without the names and signatures they pointed at.

Dropped:: `LocalVariableTable`, `LocalVariableTypeTable` and `CharacterRangeTable`; the type annotations inside
method code, which carry bytecode offsets; and the invisible type annotations of the class, its fields and its
methods.
Kept:: `LineNumberTable` and `SourceFile`, so stack traces keep their `(File.java:N)` frames; `MethodParameters`,
so reflective parameter names survive; `Signature`, so generic types survive; `SourceDebugExtension`; and every
annotation reflection can see.
Left alone:: A class with an attribute the JDK does not know, whose constant pool references a rebuilt pool could
break, and `module-info`.

What an application can observe, in dependency frames only:

* A helpful `NullPointerException` message names a local by position, `because "<local1>" is null`, instead of by
name; the line number stays. A debugger shows no local-variable names in dependency code.
* Stack traces, reflective parameter names and every annotation reflection exposes are unchanged.
* The order of `getDeclaredMethods()` may change, because the JVM orders methods by the symbols a rebuilt pool
interns. That order is unspecified, and it already differs with and without class data sharing, but code that
depends on it can notice, for example reflection-based JSON property order of a dependency's classes.
* A rewritten class has new bytes and a new CRC-32: on `benchmark-large` about 85% of the dependency classes.
Class-level composition analysis may report such a class as modified rather than as an exact match. The opt-out
keeps dependency class bytes as published, and `PRESERVE` keeps whole nested JARs byte for byte.
* Output bytes depend on the JDK that runs the build, whose class-file library chooses the pool order: a stripped
archive is byte-reproducible only when it is built with the same JDK build.

On `test-suite/samples/benchmark-large`, stripping rewrites 7,102 of the 8,428 dependency classes and saves
4,868,965 bytes, with no fallback. Measured by the startup harness (<<benchmarks>>) against the
`runner-stored-keepdebug` control, 30 interleaved pairs on an Apple M4 Pro with Homebrew OpenJDK 25.0.4.1:

[cols="40,60",options="header"]
|===
|Measure |Stripped minus tables kept

|Readiness without a JDK cache
|−12.6 ms paired median, 95% CI [−13.9, −8.1] (428.1 ms against 440.6 ms)

|Readiness with the JDK AOT cache
|−2.1 ms, 95% CI [−5.1, +1.1]: no measurable gain

|RSS at readiness with the JDK AOT cache
|−14.0 MiB (174.5 MB against 189.2 MB, median); the AOT cache is 1.7 MB smaller

|Archive size
|32,726,207 against 37,590,842 bytes raw (−12.9%), 8,344,903 against 9,686,906 bytes gzip -6 (−13.9%)
|===

Packaging does the extra work on the staging threads. With 8 of them, the sample's `micronautRunnerJar` task took
0.24 s instead of 0.08 s (medians of ten warm-daemon rounds), against 0.73 s for its `shadowJar`.

Some libraries read local-variable tables at run time and find nothing once they are gone. When the class path
contains one of them, the build keeps every table and warns once, naming the JAR and the class:

* Paranamer's `com.thoughtworks.paranamer.BytecodeReadingParanamer`;
* any class of AspectJ's weaver, under `org.aspectj.weaver`;
* Spring's `org.springframework.core.LocalVariableTableParameterNameDiscoverer`, which Spring removed in 6.1.

To keep the tables, and silence that warning, set the `stripLocalVariables` option to `false`. In Gradle:

[source,groovy]
----
micronaut {
    runner {
        options.put('stripLocalVariables', 'false')
    }
}
----

In Maven, pass `-Dmicronaut.runner.stripLocalVariables=false`, or add a `<runnerOptions>` entry:

[source,xml]
----
<configuration>
    <runnerOptions>
        <stripLocalVariables>false</stripLocalVariables>
    </runnerOptions>
</configuration>
----
