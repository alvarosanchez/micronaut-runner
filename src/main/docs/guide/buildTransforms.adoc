Packaging can do work once, at build time, that an application would otherwise repeat at every start. Each
transformation is an option of the Runner JAR, fails closed, and names in the build log why it did nothing when it
does nothing.

There are two kinds. <<precompiledLogback>> adds generated classes to the application layer, and
<<classTransforms>> rewrites classes as the archive is assembled: it <<desugaredLambdas,desugars the lambdas>> of
the dependencies and of the application's own classes, and drops the dependencies'
<<localVariableTables,local-variable tables>>. All of them are on by default, and neither kind touches what the
other produces: the generated Logback classes join the application layer after the class transforms have run, and
the Logback front end runs the application's Logback JARs as they were published, not their re-packed copies.

[[precompiledLogback]]
== Precompiled Logback configuration

Runner JARs precompile logback.xml by default; Shadow JARs, Docker images and native images configure Logback with
Joran at startup unless Micronaut AOT's `logback.xml.to.java` has replaced `logback.xml`, so switching a project from
Shadow to Runner changes how Logback is configured. The opt-out restores Joran.

Without it, Logback parses `logback.xml` on the main thread at every start: it loads the JDK's XML parser and
Joran's model classes, and `io.micronaut.runtime.Micronaut` waits for it. With it, the packager reads the file with
Logback's own parser, in an isolated class loader that holds only the application's Logback and SLF4J jars, and
generates `io.micronaut.runner.generated.logback.LogbackConfigurator`, registered as a
`ch.qos.logback.classic.spi.Configurator` service. At startup that class creates the appenders and sets the loggers
the file declares, in the order Joran does, without XML. `logback.xml` stays in the archive.

=== What is compiled

A file is compiled only when all of it is within this subset:

* `<configuration>` without `debug`, `scan`, `scanPeriod` or `packagingData`, or with them `false`;
* `<appender>` elements of public `ch.qos.logback` appender classes, such as `ConsoleAppender` and `FileAppender`,
with `String`, `boolean` or `int` properties (`<target>`, `<file>`, `<append>`) and at most one `<encoder>`, a
`PatternLayoutEncoder` whose only child is a `<pattern>` using Logback's built-in conversion words;
* `<logger>` (name, level, `additivity`) and `<root>` elements that contain only `<appender-ref>`s.

No value may use a variable. Anything else, such as `<property>`, `<include>`, `<if>`, `<conversionRule>`, a
`<filter>`, a `<rollingPolicy>` or a custom appender, leaves the file to Joran. So does a file Joran itself
corrects or complains about: two appenders writing to the same `<file>`, a property element without text, or a
`<name>` element inside an appender.

=== When nothing is compiled

The packager also leaves the file to Joran when logback-classic, logback-core or slf4j-api is missing, when the two
Logback jars differ in version or are outside 1.5.37 to 1.6 (exclusive), when there is no `logback.xml`, when any
layer has a `logback-test.xml`, `logback.groovy` or versioned Logback file, when any layer already registers a
`Configurator` (your own, or Micronaut AOT's), and when a packaged `+application*+` or `+bootstrap*+` file may set
`logger.config` or `logback.configurationFile`. That last check errs on the side of Joran: a `.properties` file is
parsed, and any other format counts when its text names `configurationFile` or `logger.config`, or has the word
`logger` and a `config` key anywhere, whatever the nesting or the line breaks. The build logs one line either way,
at info level: `Precompiled logback.xml (application layer) into ...` or `No Logback configuration was precompiled
because <reason>; Logback will configure itself with Joran at startup`. A generated class name that is already
taken is a warning.

=== At runtime

The generated configurator hands the configuration to Joran when:

* `-Dlogback.configurationFile` is set;
* Micronaut refreshes logging (any `+logger.*+` property does) and `-Dlogger.config`, `LOGGER_CONFIG`, or an
environment variable named `logger.config` or `logback.configurationFile`, names a location: that file is
configured, as without Micronaut Runner;
* `-Dlogback.debug` or `-Dlogback.statusListenerClass` asks for Logback's status output;
* `-Dmicronaut.runner.logback.precompiled=false` is set.

What changes when it applies: Joran's INFO status messages about reading `logback.xml` are not recorded, and every
way to see them falls back to Joran. `logback.xml` is read only on the paths above.

One case is not covered: a `logger.config` set by configuration outside the archive, such as
`-Dmicronaut.config.files`, an `application.yml` in the working directory or a `--logger.config` program argument,
is not applied once a `Configurator` is registered, and the runtime opt-out does not change that. Set the location
with `-Dlogger.config` or `LOGGER_CONFIG` instead, or turn precompilation off.

=== Turning it off

[source,groovy]
----
micronaut {
    runner {
        options.put('precompileLogback', 'false')
    }
}
----

In Maven, pass `-Dmicronaut.runner.precompileLogback=false`, or add `<precompileLogback>false</precompileLogback>` to
`<runnerOptions>`.

[[classTransforms]]
== Class transforms

A runner JAR re-packs every dependency, and with the default `STORED` compression, or `HYBRID`, it can also rewrite
classes on the way: whatever a class carries that the application never needs at run time, or has to work out again at every
start, is paid for on every start. This section lists what Runner changes in classes at build time, the default and
the opt-out of each change, and what an application can observe as a result.

Every change runs in one pass: each class is parsed once, every enabled transform is applied to it, and the result
is written once. Before a rewritten class is accepted it is verified, with the JDK's class-file verifier, against
the whole runtime class path and the JDK's own classes; a transform that fails on a class, or makes it verify
worse than the class it replaces, is dropped for that class alone, and the build log says so. Desugaring changes
several classes together, so there the unit is the nest: the classes of one top-level class and the ones generated
for them.

With both transforms on, as with every other default, packaging `benchmark-large` still takes less time than Shadow:
in the packaging comparison of the
https://github.com/alvarosanchez/micronaut-runner/actions/runs/36818155119[CI run] of <<benchmarkResults,Benchmarks>>
(4 vCPUs, warm Gradle daemon, `--rerun`, 10 rounds), the median `micronautRunnerJar` task action took 1167.9 ms
against 1347.1 ms for `shadowJar`, `runner-stored` − `shadow` -187.7 ms [-226.8, -113.8]. CI has no packaging row with
the transforms off; the on and off times under each transform below come from local sessions on another machine, and
do not compare with these.

Stripping never applies to the application's own classes or to a project dependency (another project of a Gradle
build, another module of a Maven reactor): they are user code, whose locals users debug. Desugaring applies to
both. Neither applies to the classes Runner generates into the application layer or to any class of a signed JAR,
which are nested exactly as they were built. With `PRESERVE` compression every dependency is nested byte for
byte, and none of these transforms run, in the application layer either.

What a build changed is recorded in the archive, in `MICRONAUT-INF/transforms.txt` (see
<<format,The Runner JAR Format>>), and printed by the `inspect` mode:

[source,bash]
----
java -Dmicronaut.runner.mode=inspect -jar build/libs/my-app-0.1-all.jar
----

[[desugaredLambdas]]
=== Desugared lambdas

On by default with `STORED` and `HYBRID` compression. A lambda or a method reference compiles to an `invokedynamic` call site,
and the first time the site runs, the JDK spins a hidden class for it. A CDS archive or an AOT cache keeps such a
class only when the calling class was defined by one of the JDK's built-in class loaders, and the classes of a
runner JAR are defined by Runner's own. So every lambda that runs before the application is ready is linked again
at every start, with or without a cache. Desugaring writes that class when the application is packaged instead:
each eligible site calls a generated class, `<Host>$$Lambda$R<n>`, stored right after its host, in the same JAR or
in the application layer. Nothing is linked at run time, and a cache holds the generated class like any other.

Rewritten:: A call site of `LambdaMetafactory.metafactory` whose implementation the generated class can call as
the site did: a member of the host's own nest, private ones included; a non-private member of the host's package;
or a public member of a public class, in any JAR or in an exported package of the JDK. The generated class
implements the same interface, keeps the captured values in final fields, and converts arguments and results as
the JDK would.
Left as `invokedynamic`:: A `super::method` reference, or any other non-virtual (`invokespecial`) reference that is
not to a private method of the host; a caller-sensitive JDK method, such as `Class::forName`; a
site whose host, or whose implementation's owner, an earlier JAR shadows or a multi-release variant replaces; a
site that would need a class that is not on the class path; every class of a signed JAR and of
`META-INF/versions/`; and every other bootstrap: string concatenation, the `ObjectMethods` of records, and
serializable or marker-interface lambdas.
Java 8 classes:: A class below class-file version 55 has no nestmates, so a private lambda body is reached through
a package-private static synthetic method, `$runner$lambda$<n>`, added to the host. Two hosts cannot take one and
keep such sites: an interface, where it would have to be public, and a serializable class that declares no
`serialVersionUID`, whose default value it would change.

What an application can observe, for the rewritten lambdas of dependency and application classes:

* `Class.isHidden()` is `false`, and the class has a stable name that `Class.forName` finds. Its name still
contains `$$Lambda`, so code that recognises lambdas by name still does.
* Each call of the lambda adds one visible frame, `<Host>$$Lambda$R<n>.<method>`, to stack traces and to
`StackWalker`, where the hidden class's frame was hidden. Code that finds its caller by walking the stack from a
method used as a method reference sees the generated class.
* The JARs and the application layer gain one `.class` resource per rewritten site, and a rewritten host and its
nest host have new bytes and a new CRC-32. Class-level composition analysis may report them as modified.
* A Java 8 host gains its `$runner$lambda$<n>` methods, which `getDeclaredMethods()` returns.
* A generated class is resolved by name, by the class loader that defined its host. A class loader of your own
that defines a copy of a host from its bytes has to be able to find the generated classes next to it as well.
* Output bytes depend on the JDK that runs the build: the archive is byte-reproducible only when it is built with
the same JDK build.

The step fails closed. Every class it writes or rewrites is verified, and when one class of a nest verifies worse
than before, or the step fails on it, the whole nest is packaged as it was, with one line in the build log. The
build log's summary line and the `lambdas` lines of `transforms.txt` give the sites rewritten, the classes
generated, the bridges added and the sites left, by reason. The sites left include those of signed JARs and of the
`META-INF/versions/` classes the runtime loads; the copies of a class that the runtime never loads are not counted.

On `test-suite/samples/benchmark-large`, desugaring rewrites 2,963 of the 2,992 lambda call sites of the
dependencies and the application, 361 of them through bridges, with no fallback; none of the 29 it leaves runs
before the application is ready. Measured by the startup harness against the `runner-stored-lambdas` control, in
the https://github.com/alvarosanchez/micronaut-runner/actions/runs/36818155119[CI run] of
<<benchmarkResults,Benchmarks>> (4 vCPUs, JDK 25.0.4.1, 20 interleaved pairs; memory at readiness as medians):

To keep every lambda an `invokedynamic` call site, set the `desugarLambdas` option to `false`. In Gradle:

[source,groovy]
----
micronaut {
    runner {
        options.put('desugarLambdas', 'false')
    }
}
----

In Maven, pass `-Dmicronaut.runner.desugarLambdas=false`, or add a `<runnerOptions>` entry:

[source,xml]
----
<configuration>
    <runnerOptions>
        <desugarLambdas>false</desugarLambdas>
    </runnerOptions>
</configuration>
----

[[localVariableTables]]
=== Local-variable tables

On by default. A dependency class loses the tables that name its local variables, and its constant pool is rebuilt
without the names and signatures they pointed at.

Dropped:: `LocalVariableTable`, `LocalVariableTypeTable` and `CharacterRangeTable`; the type annotations inside
method code, which carry bytecode offsets; and the invisible type annotations of the class, its fields and its
methods.
Kept:: `LineNumberTable` and `SourceFile`, so stack traces keep their `(File.java:N)` frames; `MethodParameters`,
so reflective parameter names survive; `Signature`, so generic types survive; `SourceDebugExtension`; and every
annotation reflection can see.
Left alone:: A class with an attribute the JDK does not know, whose constant pool references a rebuilt pool could
break, and `module-info`.

What an application can observe, in dependency frames only:

* A helpful `NullPointerException` message names a local by position, `because "<local1>" is null`, instead of by
name; the line number stays. A debugger shows no local-variable names in dependency code.
* Stack traces, reflective parameter names and every annotation reflection exposes are unchanged.
* The order of `getDeclaredMethods()` may change, because the JVM orders methods by the symbols a rebuilt pool
interns. That order is unspecified, and it already differs with and without class data sharing, but code that
depends on it can notice, for example reflection-based JSON property order of a dependency's classes.
* A rewritten class has new bytes and a new CRC-32: on `benchmark-large` about 85% of the dependency classes.
Class-level composition analysis may report such a class as modified rather than as an exact match. The opt-out
keeps dependency class bytes as published, and `PRESERVE` keeps whole nested JARs byte for byte.
* Output bytes depend on the JDK that runs the build, whose class-file library chooses the pool order: a stripped
archive is byte-reproducible only when it is built with the same JDK build.

On `test-suite/samples/benchmark-large`, stripping rewrites 7,102 of the 8,428 dependency classes and saves
4,992,144 bytes, with no fallback, as the build log of the
https://github.com/alvarosanchez/micronaut-runner/actions/runs/36818155119[CI run] shows. Measured by the startup
harness in that run (<<benchmarkResults,Benchmarks>>: 4 vCPUs, JDK 25.0.4.1, 20 interleaved pairs) against the
`runner-stored-keepdebug` control, except for the memory row:

[cols="40,60",options="header"]
|===
|Measure |Stripped minus tables kept

|Readiness without a JDK cache
|-19.8 ms paired median (-29.7 to -5.0), 939.6 ms against 952.5 ms

|Readiness with the JDK AOT cache
|-4.9 ms (-12.2 to +4.5): no measurable gain

|Maximum RSS with the JDK AOT cache, local study below
|−4.6 MB paired median, 95% CI [−4.9, −3.6] (181.9 MB against 186.3 MB)

|Archive size
|34.4 against 39.4 MiB raw (0.87×), 8.4 against 9.8 MiB gzip -6 (0.86×); the AOT cache is 45,940,736 against
47,775,744 B
|===

The memory row comes from a separate run, because the RSS of a cached start moves by several MB from one trained
cache to the next, which is more than stripping saves. It is the paired median over 40 pairs of AOT caches, each
pair trained afresh from the two archives and each archive then started three times; in 5 of the 40 pairs the
stripped archive used more, by 2.0 MB at most. It was measured locally on an Apple M4 Pro (12 CPUs) with Homebrew
OpenJDK 25.0.4.1, before Runner precompiled `logback.xml` (<<precompiledLogback>>), generated the static service table
or desugared lambdas: both archives of each pair configured Logback with Joran. The CI run trains one cache per row,
so its 5.9 MiB less RSS and 2.7 MiB less private memory (`RssAnon`) at readiness are a single training's difference,
without an interval.

Packaging does the extra work on the staging threads. Measured locally on that machine, also before the Logback
precompilation, the static service table and desugaring, with 8 staging threads, the sample's `micronautRunnerJar`
task took 0.24 s with stripping and 0.08 s without (medians of ten warm-daemon rounds).

Some libraries read local-variable tables at run time and find nothing once they are gone. When the class path
contains one of them, the build keeps every table and warns once, naming the JAR and the class:

* Paranamer's `com.thoughtworks.paranamer.BytecodeReadingParanamer`;
* any class of AspectJ's weaver, under `org.aspectj.weaver`;
* Spring's `org.springframework.core.LocalVariableTableParameterNameDiscoverer`, which Spring removed in 6.1.

To keep the tables, and silence that warning, set the `stripLocalVariables` option to `false`. In Gradle:

[source,groovy]
----
micronaut {
    runner {
        options.put('stripLocalVariables', 'false')
    }
}
----

In Maven, pass `-Dmicronaut.runner.stripLocalVariables=false`, or add a `<runnerOptions>` entry:

[source,xml]
----
<configuration>
    <runnerOptions>
        <stripLocalVariables>false</stripLocalVariables>
    </runnerOptions>
</configuration>
----
